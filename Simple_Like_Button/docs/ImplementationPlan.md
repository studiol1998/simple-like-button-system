# 実装計画メモ

このメモは、Pollyanna v1.0の既存仕様と、みやびさんと合意した設計方針を実装作業へつなぐための計画です。仕様の正本を置き換えるものではありません。合意事項は [DatabaseDesignDecisionLog.md](DatabaseDesignDecisionLog.md)、DB設計の確認事項は [DatabaseDesignReview.md](DatabaseDesignReview.md) を参照してください。

旧ベータ版は動作や移行対象を確認する参考資料として扱い、そのコードをそのまま現行版に採用しません。

## 現在の進捗（2026-10-03）

2026-10-03：本番用管理画面を実装した。Dashboard／個別詳細／設定、日英切り替え、9種類のカラーテーマ、レスポンシブ表示を備える。Dashboardは実DBから総数・集計済み・未集計・いいねID数、直近7日、直近12か月、当月時間帯別を表示する。個別詳細は月別時間帯、ID検索、対象期間、日別・月別・年別推移、累計・期間件数、20件単位のページ送り、設置先URLを表示する。設定は管理・運用とサイト表示を区分単位で保存し、タイムゾーン変更はアーカイブ・リセット・中断再開を含む独立操作として接続した。

管理画面認証も実装済み。初回はlocalhostから12文字以上の管理パスワードを設定し、ハッシュを `config/admin_credentials.json` に保存する。以後はセッション認証、ログイン成功時のセッションID更新、CSRF検証、1分5回の試行制限、ログアウトを使用する。パスワード表示切替は初期設定・ログインの両画面に設けた。

ウィジェットの `data-url` に管理者が明示したHTTP/HTTPSの正規URLを、Like IDと関連付けて保存する。閲覧中URL、リファラー、ページタイトルは自動収集しない。同じIDに複数URLを登録できる。既存環境向けに `install/upgrade-identifier-urls.sql` を用意した。

押下API、状態復元、日別・月別・年別・時間帯別集計、レート制限、日英ウィジェット、ローカル確認ページ、各種設定、タイムゾーン変更時のアーカイブを実装しています。いいね件数の自動更新は初期値5秒で、間隔の選択にも対応しました。件数表示がオフのときは初回の押下状態確認だけを行い、件数取得は行いません。集計失敗時のロールバック・再試行と2プロセス同時実行は、2026-09-29にXAMPP MariaDBの一時DBで確認済みです。

古いデータの圧縮とタイムゾーン変更の中断・再開は、2026-09-29にXAMPP MariaDBの一時DBと隔離したファイル領域で確認済みです。5年境界による日別→月別、月別→年別の移行、既存集計への加算、日別50,000行上限（50,001行から1行を月別へ移行）で件数が保持されることを確認しました。タイムゾーン変更では、500件処理後の再開、アーカイブ保護エラー時に旧タイムゾーン・集計511件・メンテナンス状態を維持すること、エラー解消後の再開とコミット後復旧を確認しました。CSV数式対策は合成テストIDを含むアーカイブを作成し、Microsoft Excelで文字列として表示され、数式が実行されないことを確認しました。テンプレートへの本設置前に残る主な作業は、実際のサイト条件での通し確認とApache以外のWebサーバー向けアクセス拒否設定です。

## 実装の目的

- サイトへ簡単に組み込める、自己ホスト型のいいねボタンを完成させる。
- 合意済みのデータ最小化、作品ごと・ブラウザ単位のレート制限、期間別集計、管理画面・インストーラーの方針を一貫して実装する。
- 実装完了後に動作確認し、みやびさんがテンプレートHTMLへ組み込める状態にする。

## 合意済み仕様の要点

- いいねは一旦個別イベントとして記録し、集計後は個別イベントを削除する。
- 自動集計開始件数は管理画面のドロップダウンで1,000件（初期値）、2,000件、4,000件、6,000件、8,000件、10,000件から選択する。しきい値到達時に自動集計を開始する。未到達分は経過時間だけでは自動集計せず、管理画面アクセス時に集計する。定期実行は設けない。
- 最新の件数は保存済み集計と未集計イベントを合わせて求める。公開件数表示は初期状態でオフにし、管理画面で切り替える。
- 公開件数を表示する場合は初期値5秒で定期更新し、10秒・30秒・60秒・更新なし（0秒）も選べる。件数表示がオフなら定期問い合わせを行わず、タブが非表示の間も更新を止める。
- 日別データは最大5年かつ最大50,000行とし、どちらかの上限に達したら古い分を月別にまとめる。直近3年程度の詳細データを見たい需要に余裕を持たせるため、日別は5年を上限とする。50,000行はプログラム設定で変更可能にする。
- 月別データは月別化してから5年間保持し、その後は年別にまとめる。年別データは保持する。
- 時間帯別集計はβ版から実装し、自サイトで試用した後に公開版へ含めるか判断する。サイト全体のいいねを、設定中のタイムゾーンで1時間単位に分けて月別集計し、直近24か月を保持する。既存の集計バッチで処理し、件数がある時間帯だけ保存する。
- タイムゾーン変更時は、未集計分も含めて現行の累計・期間別・時間帯別データを集計し、変更ごとの日時入りフォルダーを `log/` に作ってCSVで格納した後、稼働中の集計値をリセットして新しいタイムゾーンで集計を始める。公開件数も0から再開する。
- タイムゾーン変更前に確認ダイアログを表示する。［はい］の後は集計・格納の進行状況を表示し、完了後は `log/` への格納完了を通知する。処理中はサイトAPIをメンテナンスにし、中断時は管理画面から再開できるようにする。
- アーカイブに自動削除の期限は設けない。管理画面にダウンロード・削除機能は設けず、サーバー容量を圧迫する場合はログファイルを削除するよう完了ダイアログで案内する。バックアップ・削除は管理者が手動で行う。
- タイムゾーン変更ごとに日時入りフォルダーを作り、`metadata.json`、`lifetime_totals.csv`、`period_aggregates.csv`、`hourly_aggregates.csv` を保存する。CSVは `fputcsv` で出力し、数式として扱われ得る識別子には先頭にアポストロフィを付ける。
- UTCで時刻を保存する。生IPは保存せず、調査用IPハッシュは最長60日で削除する。
- レート制限はLike ID（作品）ごと・匿名ブラウザごとに適用し、直近24時間の回数を1〜5回（初期値3回）で制限する。`ip_hash` は押下拒否には使わない。
- 動作状態は有効・メンテナンスの2種類とする。

## 想定する通常運用の流れ

1. サイト訪問者がボタンを押すと、APIが識別子・ブラウザトークン・レート制限を検証し、UTC時刻と必要なハッシュを持つ個別イベントを記録する。
2. 公開件数表示が有効な場合、APIは現在の累計値に未集計イベントを加えて返す。無効の場合、公開APIは件数を返さない。
3. 未集計イベントが設定した自動集計開始件数に達した時、または管理画面を開いた時、集計処理を起動する。1回のバッチは最大500件とし、当面は管理画面から変更しない。この上限は自動集計開始件数とは別に扱い、処理を軽くする。個別記録の取得・集計値更新・処理済み個別記録の削除は、短いDBトランザクション内で行い、失敗時は全体をロールバックして再試行する。集計処理同士の並行実行を防ぐ。
4. イベント時刻を現在のタイムゾーンの日付に振り分け、累計値と日別値を更新する。古い日別データは、5年経過または日別行数上限到達のいずれかで月別にまとめる。
5. 月別になってから5年経過したデータを年別にまとめ、年別集計を保持する。
6. 時間帯別集計は既存バッチ内で月別・1時間区分ごとに更新し、直近24か月分だけ保持する。
7. レート制限用記録は集計用イベントと分離し、同一Like ID・ブラウザからの次回アクセス時に期限切れ分を削除する。調査用IPハッシュは保存開始から最長60日で削除する。

未集計件数が設定値に届かず、管理画面にもアクセスされなければ、データは未集計のまま保持します。通常バッチは最大500件で、イベント取得・集計値更新・処理済みイベント削除を同一トランザクションにまとめます。失敗時はロールバックし、DB単位のロックで並行処理を防ぎます。この失敗時の再試行と二重加算防止、2プロセスの同時実行は2026-09-29に一時DBで確認しました。公開件数表示中は設定間隔で最新件数を取り直し、非表示タブでは停止します。

### タイムゾーン変更時の流れ

1. 管理画面で変更を選ぶと、累計・期間別集計・公開件数がリセットされることを確認する。
2. ［はい］の後、未集計イベントを含む現在分の集計を完了させる。
3. 確定した累計値・期間別集計値・時間帯別集計値を、日時入りの個別フォルダーに保存する。`lifetime_totals.csv`、`period_aggregates.csv`、`hourly_aggregates.csv` と `metadata.json` に変更日時・変更前後のタイムゾーンなどを記録する。進行状況として「現在のデータを集計中」「集計したデータを格納」を表示する。
4. 格納の成功を確認してから稼働中データをリセットし、新しいタイムゾーンを適用して新規集計を開始する。
5. 完了ダイアログで `log/` が格納先であることを通知する。サーバー容量を圧迫する場合はログファイルを削除するよう案内する。アーカイブは自動削除せず、必要なバックアップ・削除は管理者が手動で行う。

アーカイブ格納に失敗した場合はDBトランザクションをロールバックし、旧タイムゾーンと稼働中データを維持します。中断時は確認ページから再開します。

## 実装の段階

### 1. 0.0.1の最小実装

- DBへ接続し、識別子と押下を保存する最小のテーブルを用意する。
- 押下を受け付けるAPIを用意する。
- ♡の表示、タップ、保存成功後の♥（色つき）表示を実装する。
- 保存成功・失敗を確認し、0.0.1の完成条件を確認する。

### 1.1 0.0.2の状態復元

- 同じブラウザトークン・同じ識別子の保存済みイベントを照会するAPIを追加する。
- ページ読み込み時にAPIへ問い合わせ、保存済みなら♥表示へ戻す。
- LocalStorageのブラウザトークンと既存テーブルを使い、DB構造は変更しない。
- 再読み込み後の復元と、別ブラウザ・別識別子との分離を確認する。

### 2. 段階拡張に向けた設計

- DBのテーブル・索引・保存形式を定める。
- `log/` はApacheの `.htaccess` でWebアクセスを拒否し、自動削除しない。
- 集計処理の分割、失敗時のロールバック、二重加算防止を実装済み。2026-09-29にXAMPP MariaDBの一時DBで障害・同時実行を確認済み。
- タイムゾーン変更の中断・再開、アーカイブ失敗後の再開、コミット後復旧を2026-09-29に隔離環境で確認済み。

### 3. データ層と中核処理

- 現行仕様に沿ったDB構築処理を用意する。
- いいね登録、作品ごと・ブラウザ単位のレート制限、公開件数取得を実装する。
- 期間別集計、月別への圧縮、期限を迎えた調査用ハッシュの削除を実装する。
- 同時アクセスや処理失敗があっても二重計上・記録消失を起こさないようにする。

### 4. APIと埋め込みウィジェット

- APIの入力検証、HTTPメソッド、応答形式、エラー応答を仕様に合わせる。
- 外部JavaScriptでボタン表示、押下、メンテナンス表示、通信エラー表示を行う。
- 将来のHTMLテンプレートに設置できる埋め込み例を用意する。

### 5. 管理画面

- メンテナンス設定、レート制限設定、公開件数表示、統計を扱う。
- タイムゾーン変更時の警告・確認、集計と `log/` 格納の進行状況、完了通知をローカル確認ページに実装済み。
- タイムゾーン変更処理では、格納が完了する前に稼働中データを消去しない。

### 6. インストーラーと運用準備

- DB接続設定、テーブル作成、秘密鍵生成、セキュリティ確認を含む導入手順を整える。
- `log/` など書き込みが必要な保存先の保護・アクセス制御を確認する。
- 日本語・英語の設置・設定ドキュメントを整える。
- 次回作業は [InstallerDesign.md](InstallerDesign.md) に沿ってWebインストーラーを実装する。

### 7. 統合確認とテンプレート移植準備

- 実際の設置条件に合わせてAPI・ボタン・管理画面・集計・タイムゾーン変更を一連で確認する。
- 自動集計しきい値を隔離MariaDBで確認済み。999件では未集計、1,000件目をAPI経由で投稿すると500件が集計された。Edgeで管理画面を開くと自動実行される30件バッチ後、画面とDBの両方で未集計470件・累計530件・合計1,000件を確認した。初期値は1,000件のまま維持する。
- 集計失敗時のロールバック・再試行・同時実行防止、古いデータの圧縮、タイムゾーン変更の復旧は隔離環境で確認済み。
- みやびさんが約20個のテンプレートHTMLへ設置できる埋め込み仕様を確定する。
- 確認完了後にテンプレートへ組み込み、その後本文パーツを移植できる状態にする。

## 後続機能の実装前に決める項目

以下は0.0.1の着手条件ではなく、該当する後続機能に着手する前に決める。

### 仕様として決める項目

1. アーカイブCSVの数式対策を実装し、2026-09-29にMicrosoft Excelで確認済み。識別子に付けたアポストロフィが表示され、値は数式として評価されなかった。
2. β版での試用後、時間帯別集計を公開版に含めるか。
3. dashboardの時間帯別グラフでは、選択した月・年の合計に対する割合を棒グラフで示し、時間ごとの実数と期間合計も併記する案がある。分母、少数件数時の見せ方、表示可能期間はdashboard設計時に決める。時間帯別データの保存は現在直近24か月の案のため、それより古い年の表示に必要な保存方法も検討する。

### 実装設計で決める項目

1. 集計バッチの上限は500件に決定済み。ロールバック・再試行・同時実行防止も隔離環境で確認済み。
2. タイムゾーン変更の復旧は隔離環境で確認済み。実際の設置先での運用手順は本番導入前に確認する。
3. 選択された件数への到達を低負荷で検出する方法。
4. Apache以外のWebサーバーでも `log/` への直接アクセスを拒否する設定。

## コミットの区切り

テンプレートへの本設置や公開準備に進む際は、その時点の実装・確認結果を整理してから、コミット範囲やタグ付けを相談する。
