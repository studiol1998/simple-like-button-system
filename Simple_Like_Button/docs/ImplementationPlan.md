# 実装計画メモ

このメモは、Pollyanna v1.0の既存仕様と、みやびさんと合意した設計方針を実装作業へつなぐための計画です。仕様の正本を置き換えるものではありません。合意事項は [DatabaseDesignDecisionLog.md](DatabaseDesignDecisionLog.md)、DB設計の確認事項は [DatabaseDesignReview.md](DatabaseDesignReview.md) を参照してください。

旧ベータ版は動作や移行対象を確認する参考資料として扱い、そのコードをそのまま現行版に採用しません。

## 実装の目的

- サイトへ簡単に組み込める、自己ホスト型のいいねボタンを完成させる。
- 合意済みのデータ最小化、ブラウザ単位のレート制限、期間別集計、管理画面・インストーラーの方針を一貫して実装する。
- 実装完了後に動作確認し、みやびさんがテンプレートHTMLへ組み込める状態にする。

## β版のバージョン計画

### 0.0.1

- ♡をタップすると、サーバーが受け付けた後に色つきの♥に変わる。
- タップ内容をデータベースに保存する。
- 入力チェックを含める。レート制限は0.0.1では設けず、管理画面・運用設定を整える0.1.0までに改めて扱う。

### 0.0.2（完成）

- 同じブラウザ・同じ識別子について、再読み込み後も押下済み状態を復元する。
- 後付けでDB構造を変えずに済むよう、ブラウザ識別の仕組みは0.0.1から考慮する。

### 0.0.3

- 押下数を表示する。
- 管理画面ができるまでは、設定ファイルで表示のオン・オフを切り替える。

### 0.0.4

- 日別・月別・年別の集計を実装する。
- サイト全体のいいねを、現在のタイムゾーンに基づいて2時間単位・月別に集計し、直近24か月を確認できる簡易表示を用意する。

### 0.1.0

- 管理画面と設置・運用に必要な機能をまとめ、自サイトで試用する。
- レート制限などの設定や、押下数表示のオン・オフを管理画面から操作できるようにする。
- 時間帯別集計を公開版に含めるかは、自サイトでの試用後に判断する。

0.0.1では、各バージョンの機能を一度に作らず、押下・DB保存の成立を優先する。通信または保存に失敗した場合の表示は必要最小限とする。

## 合意済み仕様の要点

- いいねは一旦個別イベントとして記録し、集計後は個別イベントを削除する。
- 自動集計開始件数は管理画面のドロップダウンで1,000件（初期値）、2,000件、4,000件、6,000件、8,000件、10,000件から選択する。しきい値到達時に自動集計を開始する。未到達分は経過時間だけでは自動集計せず、管理画面アクセス時に集計する。定期実行は設けない。
- 最新の件数は保存済み集計と未集計イベントを合わせて求める。公開件数表示は初期状態でオフにし、管理画面で切り替える。
- 日別データは最大5年かつ最大50,000行とし、どちらかの上限に達したら古い分を月別にまとめる。直近3年程度の詳細データを見たい需要に余裕を持たせるため、日別は5年を上限とする。50,000行はプログラム設定で変更可能にする。
- 月別データは月別化してから5年間保持し、その後は年別にまとめる。年別データは保持する。
- 時間帯別集計はβ版から実装し、自サイトで試用した後に公開版へ含めるか判断する。サイト全体のいいねを、設定中のタイムゾーンで2時間単位に分けて月別集計し、直近24か月を保持する。既存の集計バッチで処理し、件数がある時間帯だけ保存する。
- タイムゾーン変更時は、未集計分も含めて現行の累計・期間別データを集計し、変更ごとの日時入りフォルダーを `log/` に作ってCSVで格納した後、稼働中のデータをリセットして新しいタイムゾーンで集計を始める。公開件数も0から再開する。
- タイムゾーン変更前に確認ダイアログを表示する。［はい］の後は集計・格納の進行状況を表示し、完了後は `log/` への格納完了を通知する。
- アーカイブに自動削除の期限は設けない。管理画面にダウンロード・削除機能は設けず、サーバー容量を圧迫する場合はログファイルを削除するよう完了ダイアログで案内する。バックアップ・削除は管理者が手動で行う。
- タイムゾーン変更ごとに日時入りフォルダーを作り、`metadata.json`、`lifetime_totals.csv`、`period_aggregates.csv` を保存する。累計CSVは `identifier,total_likes`、期間別CSVは `period_type,period_start,identifier,like_count` の列とする。
- UTCで時刻を保存する。生IPは保存せず、調査用IPハッシュは最長60日で削除する。
- レート制限はシステム全体でブラウザ単位に適用する。`ip_hash` は押下拒否には使わない。
- 動作状態は有効・メンテナンスの2種類とする。

## 想定する通常運用の流れ

1. サイト訪問者がボタンを押すと、APIが識別子・ブラウザトークン・レート制限を検証し、UTC時刻と必要なハッシュを持つ個別イベントを記録する。
2. 公開件数表示が有効な場合、APIは現在の累計値に未集計イベントを加えて返す。無効の場合、公開APIは件数を返さない。
3. 未集計イベントが設定した自動集計開始件数に達した時、または管理画面を開いた時、集計処理を起動する。処理は上限付きの小さな単位で進め、保存に成功した分だけ個別イベントを削除する。
4. イベント時刻を現在のタイムゾーンの日付に振り分け、累計値と日別値を更新する。古い日別データは、5年経過または日別行数上限到達のいずれかで月別にまとめる。
5. 月別になってから5年経過したデータを年別にまとめ、年別集計を保持する。
6. 時間帯別集計は既存バッチ内で月別・2時間区分ごとに更新し、直近24か月分だけ保持する。
7. レート制限用記録は制限時間後に削除し、調査用IPハッシュは保存開始から最長60日で削除する。個別イベントが残っていても、期限を過ぎたIPハッシュは別途消去できる設計が必要。

未集計件数が設定値に届かず、管理画面にもアクセスされなければ、データは未集計のまま保持します。1回あたりの処理量と失敗からの再開方法は実装設計で決めます。

### タイムゾーン変更時の流れ

1. 管理画面で変更を選ぶと、累計・期間別集計・公開件数がリセットされることを確認する。
2. ［はい］の後、未集計イベントを含む現在分の集計を完了させる。
3. 確定した累計値・期間別集計値・時間帯別集計値を、日時入りの個別フォルダーに保存する。既定のファイルは `lifetime_totals.csv` と `period_aggregates.csv` とし、時間帯別データの保存形式も実装設計で定める。`metadata.json` に変更日時・変更前後のタイムゾーンなどを記録する。進行状況として「現在のデータを集計中」「集計したデータを格納」を表示する。
4. 格納の成功を確認してから稼働中データをリセットし、新しいタイムゾーンを適用して新規集計を開始する。
5. 完了ダイアログで `log/` が格納先であることを通知する。サーバー容量を圧迫する場合はログファイルを削除するよう案内する。アーカイブは自動削除せず、必要なバックアップ・削除は管理者が手動で行う。

格納に失敗した場合に旧タイムゾーンと稼働中データを維持するなど、安全な失敗時動作を実装設計で定めます。

## 実装の段階

### 1. 0.0.1の最小実装

- DBへ接続し、識別子と押下を保存する最小のテーブルを用意する。
- 押下を受け付けるAPIを用意する。
- ♡の表示、タップ、保存成功後の♥（色つき）表示を実装する。
- 保存成功・失敗を確認し、0.0.1の完成条件を確認する。

### 1.1 0.0.2の状態復元

- 同じブラウザトークン・同じ識別子の保存済みイベントを照会するAPIを追加する。
- ページ読み込み時にAPIへ問い合わせ、保存済みなら♥表示へ戻す。
- LocalStorageのブラウザトークンと既存テーブルを使い、DB構造は変更しない。
- 再読み込み後の復元と、別ブラウザ・別識別子との分離を確認する。

### 2. 段階拡張に向けた設計

- DBのテーブル・索引・保存形式を定める。
- `log/` の保存方針を確定する。
- 集計処理の分割、失敗時の再開、二重加算防止を設計する。
- タイムゾーン設定の変更操作が失敗した場合の安全な復旧動作を決める。

### 3. データ層と中核処理

- 現行仕様に沿ったDB構築処理を用意する。
- いいね登録、ブラウザ単位のレート制限、公開件数取得を実装する。
- 期間別集計、月別への圧縮、期限を迎えた調査用ハッシュの削除を実装する。
- 同時アクセスや処理失敗があっても二重計上・記録消失を起こさないようにする。

### 4. APIと埋め込みウィジェット

- APIの入力検証、HTTPメソッド、応答形式、エラー応答を仕様に合わせる。
- 外部JavaScriptでボタン表示、押下、メンテナンス表示、通信エラー表示を行う。
- 将来のHTMLテンプレートに設置できる埋め込み例を用意する。

### 5. 管理画面

- メンテナンス設定、レート制限設定、公開件数表示、統計を扱う。
- タイムゾーン変更時の警告・確認、集計と `log/` 格納の進行状況、完了通知を実装する。
- タイムゾーン変更処理では、格納が完了する前に稼働中データを消去しない。

### 6. インストーラーと運用準備

- DB接続設定、テーブル作成、秘密鍵生成、セキュリティ確認を含む導入手順を整える。
- `log/` など書き込みが必要な保存先の保護・アクセス制御を確認する。
- 日本語・英語の設置・設定ドキュメントを整える。

### 7. 統合確認とテンプレート移植準備

- 実際の設置条件に合わせてAPI・ボタン・管理画面・集計・タイムゾーン変更を一連で確認する。
- 集計処理のテストでは、本番初期値の1,000件をテスト用に20件へ下げる。このテスト設定は本番仕様の初期値を変更しない。
- 20件到達時に自動集計が始まること、20件未満では1時間経過後も自動集計されないこと、未到達データが管理画面アクセス時には集計されること、再実行で二重加算しないことを確認する。
- みやびさんが約20個のテンプレートHTMLへ設置できる埋め込み仕様を確定する。
- 確認完了後にテンプレートへ組み込み、その後本文パーツを移植できる状態にする。

## 後続機能の実装前に決める項目

以下は0.0.1の着手条件ではなく、該当する後続機能に着手する前に決める。

### 仕様として決める項目

1. アーカイブCSVで識別子を表計算ソフトの数式として誤評価させない具体的な出力方法。
2. β版での試用後、時間帯別集計を公開版に含めるか。

### 実装設計で決める項目

1. 集計処理の一回あたりの上限、再開位置、同じイベントを二度加算しない方法。
2. タイムゾーン変更時の集計・ファイル格納・リセットを安全に完了させる手順。
3. 選択された件数への到達を低負荷で検出する方法。
4. `log/` の保存先とWebからの直接アクセス防止方法。親仕様書のディレクトリ一覧は `logs/` と記載されているため、現行の指示である `log/` との名前を実装時に整合させる。
