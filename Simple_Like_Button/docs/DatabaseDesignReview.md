# データベース設計の確認メモ

このメモは、プロジェクト直下にある現行仕様書と設計草案を、最初の実装に向けて整理したものです。仕様書に代わるものではなく、未決の動作や設計を確定するものでもありません。

## 現行資料で決まっている要件

- いいねのイベントを記録し、集計値は保存せずイベントから計算する。
- ページタイトル、URL、リファラー、生のIPアドレス、生のブラウザ識別値、User-Agentは保存しない。
- `identifier` は意味を解釈しない識別子として扱う。UTF-8（`utf8mb4`）、最大50文字とし、前後の空白を除去してから検証する。空文字、改行、NULL文字は受け付けない。
- 送信時刻 `created_at` を保存し、期間別集計に使う。
- レート制限用の `client_hash` を保存する。
- レート制限回避への補助策として、設置ごとの秘密鍵を使ったHMAC-SHA-256で `ip_hash` を作成する。秘密鍵はデータベースではなく、生成する設定ファイルに保存する。
- 設定としてメンテナンス状態とレート制限の時間・回数を扱う。

## 現行資料から読み取れる候補項目

### `likes` テーブル

| 項目 | 決まっていること | 追加で決めること |
| --- | --- | --- |
| `id` | いいねイベントの識別子 | 整数の範囲、自動採番の方式 |
| `identifier` | UTF-8、最大50文字、前後空白除去後に空でないこと | SQL上の型と照合順序 |
| `created_at` | 送信時刻。期間別集計に使う | 保存するタイムゾーンとSQL上の型 |
| `client_hash` | クライアント側の識別値をもとにしたレート制限キー | 長さ・型、識別値の扱いと更新方法 |
| `ip_hash` | HMAC-SHA-256による補助的なレート制限キー | 長さ・型、IPを取得できない場合の扱い |

### `settings` テーブル

草案では、メンテナンス状態、制限時間、制限回数が挙げられています。一行だけに制限する方法、許容値、旧ベータ版のような停止モードを設けるかどうかは未定です。

## `install.sql` の確定前に確認したいこと

1. レート制限は、設置全体で利用者ごとに適用するか、利用者と `identifier` の組み合わせごとに適用するか、または両方か。旧ベータ版はIPアドレス単位で設置全体に適用していましたが、現行仕様では確定していません。
2. いいねイベントをいつまで保存するか。全件を保存し続けるのか、保存期間を決めるのか。期間別統計やデータ量に影響します。
3. 日・週・月の集計に使うタイムゾーンは何か。現行資料にはタイムゾーンと週の開始曜日の指定がありません。
4. 現行システムの状態は有効・メンテナンスのみか、停止状態も設けるか。v1.0の管理仕様はメンテナンスのみですが、旧ベータ版は3状態でした。
5. クライアント識別値をどう作成・保存・更新するか。草案にはCookieとLocalStorageの記載がありますが、優先順や再発行時の扱いは未定です。

これらは未決のまま記載しています。旧ベータ版の挙動だけを根拠に決定しません。
