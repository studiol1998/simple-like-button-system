# 実装計画メモ

制作者：にくきぅSYSTEMs（Nikukiu-SYSTEMs）

このメモは、開発履歴、β-2の現行仕様、正式公開までの作業、公開後の検討課題を整理した実装計画メモである。既存の仕様の正本を置き換えるものではない。\
決定事項は [DatabaseDesignDecisionLog.md](DatabaseDesignDecisionLog.md)、DB設計の検討事項は [DatabaseDesignReview.md](DatabaseDesignReview.md) を参照する。

本書では、identifier（識別子）を、いいねの集計対象を区別するための値と定義する。\
管理画面などで使用する「Like ID」は、この identifier と同じものを指す。

自己ホスト型の「いいねボタン」の作成にあたり、まずは以下の仕様を想定した。

- 軽量に設置できる
- データ最小化
- 作品ごと・ブラウザ単位の押下制限、期間別集計、管理画面
- インストーラーを一貫して実装できる

本作業に着手する前に、テストタイプ（旧ベータ版）を作成した。
旧ベータ版は動作や移行対象を確認する参考資料とし、そのコードをそのまま現行版に採用しない。

状態は

- 「実装済み」
- 「検証済み（記録された環境・範囲のみ）」
- 「実サイトでの検証待ち」「仕様・実装の再確認が必要」

を区別する。また、一つの機能に複数の状態が併存する。
β-2は正式版ではなく、実サイト試験前のプレリリースである。

2026-10-09：公開ウィジェットの状態取得と件数自動更新をidentifier単位へ集約した。\
同一identifierの複数ボタンは1回の初期取得と1本の定期タイマーを共有し、Like成功結果は全ボタンへ即時反映する。\

Firefoxで確認された `Permission denied to access property "nodeType"` は継続POSTとの因果関係が確認できていないため、DOM処理を変更せず継続調査事項とする。

古いデータの圧縮とタイムゾーン変更の中断・再開は、2026-09-29にXAMPP MariaDBの一時DBと隔離したファイル領域で確認済み。\

タイムゾーン変更では、500件処理後の再開、アーカイブ保護エラー時に旧タイムゾーン・集計511件・メンテナンス状態を維持すること、エラー解消後の再開とコミット後復旧を確認。\
CSV数式対策は合成テストIDを含むアーカイブを作成し、Microsoft Excelで文字列として表示され、数式が実行されないことを確認した。\
テンプレートへの本設置前に残る主な作業は、実際のサイト条件での通し確認とApache以外のWebサーバー向けアクセス拒否設定。

### 1-5. 統合確認の補足記録

自動集計しきい値を隔離MariaDBで確認している。\
999件では未集計、1,000件目をAPI経由で投稿すると500件が集計された。\
Edgeで管理画面を開き、自動実行された30件バッチ後に未集計470件・集計済み530件・合計1,000件を画面とDBで確認した記録である。\
自動集計開始の初期値1,000件は維持した。

この30件は当時の確認条件の記録であり、現行管理画面の通常バッチ上限を30件と確定するものではない。通常バッチ500件との対応は2-9で確認事項とする。

## 第2章：現行仕様（β-2）

### 2-1. ボタンの設置と識別子管理

【実装済み／隔離環境で部分検証済み／実サイトでの検証待ち】

- 外部JavaScriptでボタン表示、押下、メンテナンス・通信エラー表示を行う。
- APIは入力、HTTPメソッド、応答形式・エラーを検証。
- 埋め込み例とコピー機能、手動識別子・自動識別子の説明を備える。
- 自動生成識別子は異なるページ間で重複し得るため、集計対象を固定するときは手動識別子を使用。

同一ページ内の同一識別子のボタンは初回取得と更新タイマーを共有し、成功結果を全ボタンに反映する。二重のlike.js読み込みを防止する。\
押下状態はブラウザトークン・localStorageを利用し、集計後のイベント削除に備える。\
localStorage消去時は別の利用者として扱う前提であり、個人を恒久的に識別する仕組みではない。

設置先URLはdata-url、canonical、og:url、現在URLの順で取得し、query・fragmentを除外して押下成立後にだけ識別子と関連付ける。\
同じ識別子に複数URLを登録でき、リファラー・ページタイトルは収集しない。\
既存環境向けの識別子URL追加SQLの存在は履歴として保持するが、β-2配布物からの既存環境更新を検証済みとするものではない。

### 2-2. 押下制限・公開件数・動作状態

【実装済み／専用DB・回帰試験で範囲を限定して検証済み／実サイトでの検証待ち】

- 押下制限はidentifier（識別子）ごと・匿名ブラウザごとの直近24時間で、1～5回、初期値3回。\
  IPを同一人物判定として使う押下上限ではない。ただし、別系統の異常アクセス対策による拒否と混同しないようにする。\
  前工程では0→3件と4回目の制限、別識別子の独立を確認。

- 公開件数は初期状態で非表示。
- 有効時は集計済みと未集計を加えた最新件数を返し、無効時は公開APIから件数を返さない。
- 定期更新は5秒（初期値）、10秒、30秒、60秒、0秒（更新なし）から選択。
- 非表示設定では初回状態照会のみを行い、件数取得を行わない。
- タブ非表示中・メンテナンス中は更新停止、通信失敗時は最大60秒の指数バックオフを使用する。

基本の動作状態は有効・メンテナンスの2種類。\
FirefoxのnodeTypeアクセスエラーと継続POSTの因果関係は未確認であり、対策完了とは記載しない。

### 2-3. データ記録と通常集計

【実装済み／隔離DBで障害・並行処理を検証済み／実サイト負荷は未検証】

1. APIで識別子・ブラウザトークン・押下上限を検証し、UTC時刻の個別イベントを保存。\
イベントと押下制限用記録は分離する。
2. 公開件数表示が有効なら、累計集計値と未集計イベント数を合算する。
3. 自動集計開始件数は1,000（初期値）、2,000、4,000、6,000、8,000、10,000件から選択。\
しきい値到達時、または管理画面アクセス時に集計。\
未到達分を時間経過だけで処理する定期実行・cronは設けない。
4. 通常バッチの既定上限は500件とし、自動集計開始件数とは別に扱う。\
当面は管理画面からバッチ上限を変更しない方針。\
個別記録取得・集計値更新・処理済み個別記録削除を同一トランザクションで行い、失敗時はロールバックして再試行する。\
DB単位のロックで集計処理同士の並行実行を防止する。
5. 現在のタイムゾーンで日付を振り分け、累計・日別・時間帯別集計を更新する。\
集計済みの個別イベントは削除する。
6. 押下制限用記録は、同一識別子・ブラウザからの次回アクセス時など、対応する経路で期限切れ分を削除する。\
IP関連データの保持は2-9の再確認事項と分ける。

未集計件数がしきい値未満で、管理画面にもアクセスがなければ、未集計のまま保持する。\
索引・保存形式の設計、二重加算・記録消失防止、500件分割、失敗時の再試行・2プロセス同時実行は元メモの設計・検証事項を引き継ぐ。

### 2-4. 日別・月別・年別・時間帯別の保持

【集約機構は実装済み／境界・件数保持の隔離試験記録あり／仕様と実装の再確認が必要】

- 「日別最大5年かつ最大50,000行」、「どちらかの上限で古い分を月別へ」
- 「直近3年程度の詳細を見たい需要に余裕を持たせるため5年」
- 「50,000行はプログラム設定で変更可能」
- 「月別化してから5年で年別へ」「年別は保持」

これらは判断経緯として保持する。現在の実装がすべてこの文面どおりであるとは断定せず、2-9の相違・確認事項として扱う。\
安全性・件数保持・正常動作・利用者向け説明に影響する相違は、3-1の方針に従って正式公開前に確認し、必要な修正を行う。仕様拡張は、現行仕様の不具合確認と分けてv1.0.1以降に検討する。

静的に確認した実装には、日別→月別、月別→年別への集約、50,000行定数、件数超過時の古い行の段階的集約がある。\
上限適用範囲、厳密な境界と解消までの回数、月別保持の起算点、変更可能な設定の所在については、2-9に記載した相違・確認事項がある。\
5年間の日別保存を無条件に保証する仕様ではなく、件数条件との関係を再検証すること。\
サイトに設置する識別子の数と増加傾向、サーバーおよびDBの性能、サイトPVなどによるレコードの増加を試算・検討した上での改修判断が必要と思われる。

時間帯別はサイト全体の月別・1時間区分で、現在のタイムゾーンに基づき、直近24か月を既存バッチで処理し、件数がある区分だけ保存する方針・実装。\
保持範囲の削除タイミングも実サイトで確認する。\
既に実装されていることと、正式版での採用判断が元メモでは試用後として残っていることを区別する。

### 2-5. 管理画面

【実装済み／ログイン・設定保存など隔離環境で検証済み／実ブラウザ・実サイトでの確認待ち】

- Dashboard、個別詳細、設定、日英切替、9種類のカラーテーマ、レスポンシブ表示を備える。
- Dashboardは総数・集計済み・未集計・識別子数、直近7日、直近12か月、当月時間帯別を表示する。
- 個別詳細はID検索、対象期間、日別・月別・年別推移、累計・期間件数、20件単位のページ送り、設置先URL、月別時間帯を扱う。

管理・運用設定とサイト表示設定を区分ごとに保存する。\
メンテナンス、押下制限、公開件数表示・色、集計しきい値を操作し、動作テスト・埋め込み例を確認できる。\
タイムゾーン変更はアーカイブ・リセット・中断再開を含む独立した操作。

### 2-6. タイムゾーン変更・アーカイブCSV

【実装済み／隔離環境で中断復旧・CSV数式対策を検証済み／設置先運用手順は確認待ち】

1. 管理画面で累計・期間別・時間帯別集計と公開件数のリセットを確認。
2. ［はい］の後、サイトAPIをメンテナンスにし、未集計イベントを含む現在分を集計。\
「現在のデータを集計中」「集計したデータを格納」と進行状況を表示。
3. log/に変更ごとの日時入りフォルダーを作り、metadata.json、lifetime_totals.csv、period_aggregates.csv、hourly_aggregates.csvを保存。\
メタデータには変更日時・変更前後のタイムゾーンなどを記録する。
4. 格納成功後だけ稼働中データをリセットし、新タイムゾーンを適用する。\
公開件数は0から再開し、元データとの合算はしない。
5. 完了通知で保存先を示す。\
自動削除期限や管理画面でのダウンロード・削除機能は設けず、容量を圧迫する場合は必要なバックアップ後に管理者が手動で削除する。

CSVは`fputcsv`で出力し、数式扱いされ得る識別子にアポストロフィを付加。\
Excelで値が文字列として表示され数式が実行されないことは2026-09-29の試験記録で確認済み。\
汎用的な統計CSVダウンロード画面まで実装済みという意味ではない。

格納失敗時はDB処理をロールバックし、旧タイムゾーンと稼働中データを維持する。\
中断時は管理画面の確認・再開経路から復旧する。500件処理後の再開、保護エラー時の511件維持、エラー解消後の再開・コミット後復旧は第1章の記録を参照する。

### 2-7. インストーラー・設置条件

【実装済み／配布物からの専用DB新規インストールを検証済み／実ホスト条件は未検証】

「ようこそ」、環境確認、DB設定、基本設定、実行確認、インストール、完了の7段階で遷移。\
専用の空DB・ユーザー・必要な権限と5種類の接続情報、ホスティング環境のDB名・ユーザー名接頭辞を事前に案内する。\

インストール後は`install/`全体を除去するまで管理画面をログイン前にロックし、設定・認証情報・完了マーカーで再実行を防ぐ。\
簡単に言うと、`install/` をサーバーから削除しない限り、管理画面に入れない仕様。\
`config/`と`log/`のApacheアクセス拒否設定を備え、インストーラーは`config/.htaccess`も確認する。Apache以外では同等の拒否設定が必要で、ファイルの存在だけで実環境の保護を保証しない。\
公開領域外への分離インストールは現時点で未検証・未対応。v1.0.1での実装・検証を目標とする。

本プログラムの最低動作要件はPHP 8.3とし、PHP 8.2以前の環境はサポート対象外とする。\
ただし、実装側の要件判定との整合は今後の確認事項とする。\
安全かつ安定した運用のため、セキュリティサポート期間内で、必要なセキュリティ修正が適用されたPHPを使用すること。\
現時点で動作検証を実施した環境はPHP 8.5.12であり、その他のバージョンについては正常動作を保証するものではない。

第2章の原設計判断を保持しつつ、実測と検証に基づいて判断することとする。

### 4-3. 暫定的な負荷モデル

自サイトの現在の設置想定を300識別子以上、1年後を400識別子以上とする。\
日次押下識別子率を40～60％と仮定し、400識別子なら1日に160～240識別子で少なくとも1回の押下が起きるモデルを用いる。

40～60％は実測値ではなく、サイト運営経験に基づく暫定的な設計仮定である。\
日々の変動が大きくなり得るため、週・月単位で平均的な負荷を捉える値として扱う。これは押下総数や毎日一定の新規行数を保証する値ではない。

日別レコードが識別子×日付につき1行生成されるか、件数上限がシステム全体かについては、2-9の静的観測を検証仮説とし、実装経路と実DBで確認する。\
未確認条件から保持年数を確定計算しない。

### 4-4. 検証環境

高性能な共用サーバー環境と、標準的な共用サーバー環境の双方を想定し、データ保持・集約処理の動作および負荷を検証する。

特定事業者・プランを必須条件にはしない。\
識別子数、日次の活動分布、データ量、集約処理、管理アクセス頻度などの試験条件を記録し、環境差と結果の適用範囲を明示する。
