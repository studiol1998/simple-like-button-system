# データベース設計の決定ログ

この文書では、設計項目を一つずつ相談し、合意した方針と未決事項を記録します。

## 1. レート制限とハッシュの保存

### 合意した方針

- レート制限はLike ID（作品）ごと・匿名ブラウザごとに適用する。直近24時間の押下回数で判定し、管理画面で1〜5回を選択する。初期値は3回。
- ランダムなブラウザトークンはLocalStorageに保存し、サーバーにはトークンそのものではなくHMAC値を保存する。
- `ip_hash` は押下制限には使わず、不正状況の調査に使う。
- 調査用のIPハッシュ記録は最長60日で削除し、生のIPアドレスは保存しない。
- レート制限の判定記録は集計用の個別Like記録と分け、直近24時間の判定に必要な間だけ保持する。期限切れ分は同じLike ID・ブラウザから次に押下があった時に削除する。

### 設計上の含意

`client_hash` と調査用 `ip_hash` は目的と保存期間が異なります。レート制限用の短期記録と60日間の調査ログを、別の記録または別の保存期間として管理します。IPハッシュは共有回線の利用者を巻き込むおそれがあるため、押下を拒否する基準には使いません。ログイン認証を行わないため、この制限は個人ではなく匿名ブラウザ単位です。

## 2. 長期記録と集計

### みやびさんの希望

- 日別の集計は最大5年分とし、それより古い日別データは月別にまとめる。
- 日別集計の上限は50,000行とする。日別データが5年を超えた時、または行数が50,000に達した時の早い方で、古い日別データを月別にまとめる。
- 50,000行は初期仕様値とし、運用開始後にプログラムの設定変更で調整できる設計にする。
- 日別データを5年残すのは、詳しく見たい直近3年分をカバーし、集計タイミングのずれなどで必要な詳細データが早く月別化されるのを避けるための余裕を持たせる。
- 個々のいいねに結びつくハッシュ値は、レート制限や調査に必要な期間だけ保持する。
- 個々の送信時刻は、統計に集約した後は保持しなくてもよいのではないか。
- 管理画面を開いたときに長期間分を一括集計する方式は遅く、サーバー負荷も大きいので避けたい。
- 自動集計開始件数は管理画面のドロップダウンから選択する。候補は1,000件（初期値）、2,000件、4,000件、6,000件、8,000件、10,000件とする。選択件数は自動集計開始のしきい値であり、一回の集計処理量とは別に設計する。
- 未集計件数が選択したしきい値に達した時は自動で集計を開始する。しきい値未達のデータは、経過時間だけでは自動集計せず、管理画面にアクセスした時に集計を開始する。定期実行タスクは設けない。
- サイト上のいいね件数表示は既定でオフとし、管理画面でオン・オフを選べるようにする。管理画面内の統計表示は別に扱う。

### 合意した集計の考え方

新しいいいねはまず個別記録として保存し、過去の記録は集計値へまとめた後に削除します。集計値と未集計の個別記録を分けて持ち、通常の表示では両方を合わせて最新値を出します。

自動集計開始件数は管理画面のドロップダウンから選択します。候補は1,000件（初期値）、2,000件、4,000件、6,000件、8,000件、10,000件です。未集計件数が選択値に達した時は自動集計を開始します。件数が選択値に届かない場合、経過時間だけでは自動集計せず、管理画面へのアクセス時に集計します。定期実行タスクは設けません。選択件数は起動しきい値であり、一回の集計処理量や未集計データの厳密な上限ではありません。サイト上で件数表示を有効にした場合は、過去の集計値に未集計記録の件数を加えて表示します。件数表示を無効にした場合、公開用APIから件数を返しません。

1回の集計バッチは500件とし、当面は管理画面から変更しない。1回あたりの処理を抑えて動作を軽くするための上限であり、自動集計の開始しきい値とは別である。しきい値に届かないデータも、管理画面へのアクセス時に集計を開始する。実運用で必要性が確認できた場合に上限の変更方法を再検討する。

集計は短いDBトランザクション方式とする。1バッチ内で対象の個別記録を取得し、集計値を更新し、処理済みの個別記録を削除するところまでを同一トランザクションで行う。途中で失敗した場合は全体をロールバックし、同じ個別記録から再試行する。集計処理同士の並行実行を防ぐロックを設ける。

集計では、個別記録にある送信時刻を使って該当する統計期間へ振り分けます。通常の一回のバッチは最大500件です。対象イベントの取得、集計値の更新、処理済みイベントの削除を同一トランザクションで行い、失敗時はロールバックします。DB単位の排他ロックで集計の並行実行を防ぎます。イベントが削除されるのは集計値と同じトランザクションがコミットされた時だけなので、失敗後に再実行しても二重加算しません。確認ページで一度に処理する件数は30件に制限します。

長期保存する統計は次の二種類を基本とします。

- **累計値**：識別子ごとの総いいね数。現在のタイムゾーンでの運用中に保持し、タイムゾーン変更時にはログへ退避したうえでリセットする。
- **期間別集計値**：日別データは5年または50,000行の上限まで保持し、いずれかに達した時は古い分を月別にまとめる。月別データは月別化してから5年間保持し、その後は年別にまとめる。年別データは保持する。50,000行は後から設定変更できる値とする。
- **時間帯別集計値**：β版から記録・管理画面表示を実装し、自サイトでの試用後に公開版へ含めるか判断する。システム全体のいいねを、現在のタイムゾーンにおける1時間単位で月別にまとめ、直近24か月分を保持する。個別イベントを既存の集計処理で処理する際に集計し、件数がある時間帯だけ保存する。24か月より古い時間帯別データは削除する。

この方法なら、個々のイベント時刻やハッシュを長期間持たずに集計を保存できます。ただし集計後に個別イベントから再計算・訂正はできません。日別データは5年または50,000行のいずれかの上限に達した時に古い分を月別にまとめ、月別として5年経過後に年別へまとめます。年別データは保持します。直近3年程度の詳細データを見たい需要に余裕を持たせるため、日別の年齢上限を5年とします。ただし、50,000行の上限が先に来た場合は、5年より前に古い日別データを月別化します。

タイムゾーンの変更は運用する国・地域の変更として扱い、過去の集計を新しいタイムゾーンで組み替えません。変更時には、未集計のいいねも含めてそれまでの累計値・期間別集計値・時間帯別集計値を確定し、`log/` に保存します。その後、稼働中の集計データをリセットして新しいタイムゾーンで新規集計を開始します。リセットにより公開件数も0から再開します。

タイムゾーン変更の確定前に、これまで積み上げたデータがリセットされることを説明する確認ダイアログを表示します。利用者が［はい］を選択した後は、進行状況ダイアログに「現在のデータを集計中」「集計したデータを格納」と段階を表示します。格納完了後は、データが `log/` に格納されたことを通知し、サーバー容量を圧迫する場合はログファイルを削除するよう案内します。必要に応じたローカルバックアップやサーバー上のファイル削除は、管理者がサーバー上で手動で行います。アーカイブに自動削除の期限は設けません。

タイムゾーン変更ごとに日時を含むフォルダーを `log/` 内に作成し、変更日時・変更前後のタイムゾーンなどを `metadata.json` に記録します。集計データは `lifetime_totals.csv`、`period_aggregates.csv`、`hourly_aggregates.csv` に保存します。CSVは `fputcsv` で出力し、数式として扱われ得る識別子には先頭にアポストロフィを付けます。アーカイブは自動削除しません。管理画面にダウンロード・削除機能は設けず、必要なローカルバックアップやサーバー上の削除は管理者が手動で行います。

変更処理中はサイトAPIをメンテナンス状態にし、未集計イベントを最大500件ずつ処理します。全データのCSVアーカイブが完成してから、集計テーブルの消去と新タイムゾーンの保存を行います。アーカイブまたはDB処理に失敗した場合、DBトランザクションをロールバックし、元のタイムゾーンを維持します。中断時は管理画面から処理を再開できる状態を保存します。Apacheでは `log/.htaccess` で直接アクセスを拒否します。

### 実装後の確認結果（2026-09-29）

XAMPPのMariaDB 10.4.32上に一時データベース `pollyanna_integration_tmp` を作成し、確認後に削除しました。時間帯別集計への意図的なSQLエラーで、元イベント2件が残り、累計・期間別・時間帯別の各集計がすべて未変更であることを確認しました。エラー解除後の再実行では2件だけを反映し、続けて実行した集計は0件となり、二重加算がないことを確認しました。さらにPHPプロセス2つを同時に動かし、一方が2件を処理、もう一方が0件を処理し、最終累計2件・未集計0件となることを確認しました。

同じく隔離した一時DBとファイル領域で、古い日別・月別データの圧縮と日別50,000行上限、タイムゾーン変更の中断・再開も確認しました。アーカイブ保護に失敗した場合は旧タイムゾーン・集計データ・メンテナンス状態を保ち、設定を直して再開するとアーカイブ・集計リセット・状態復帰まで完了しました。コミット後に中断した状態からの復旧も確認しました。

合成識別子 `=1+1`、`+SUM(1,1)`、`-1+1`、`@SUM(1,1)` などを含むアーカイブCSVを一時DBから生成し、Microsoft Excelで開きました。`lifetime_totals.csv` のA列と `period_aggregates.csv` のC列で、先頭アポストロフィ付きの文字列として表示され、数式は評価されませんでした。確認用アーカイブはXAMPPの `log/csv-safety-test-20260929/` に置き、テスト専用と明記しました。

## 3. 集計後の押下済み状態

### 合意した方針

- 集計後に個別イベントを削除しても、同じブラウザ・同じ識別子の♥状態を復元できるよう、押下済み識別子をブラウザのLocalStorageに保存する。
- サーバー側では既存の未集計イベントを状態確認に使い、押下済みであることが分かった場合はブラウザ側にも保存する。
- LocalStorageが消去された場合は別の利用者として扱う。押下状態を維持するためだけに、サーバーへブラウザ別の履歴を長期保存しない。

## 4. Dashboardでの時間帯別集計表示（設計時に検討）

時間帯別集計は、dashboardで月別または年別に表示する案がある。時間ごとの割合を棒グラフで示し、その上下などに実数を併記する。対象期間の合計件数も表示し、割合だけで誤解しないようにする。割合の分母や少数件数時の見せ方、表示期間はdashboard設計時に決める。

現在の保存案は時間帯別データを直近24か月分とする。年別表示は保存されている月別値を合算して作れるが、24か月より古い年を表示する場合は、年別時間帯集計を別途保存するかどうかをdashboard設計時に検討する。

## 5. 設置先URLと管理認証（2026-10-03）

- 閲覧中URLを自動取得せず、設置者がウィジェットの `data-url` に明示したHTTP/HTTPSの正規URLだけを保存する。
- URLは `pollyanna_identifier_urls` に保存し、Like IDとURLのSHA-256を複合主キーとする。同じIDに複数URLを許可する。
- URLに認証情報またはフラグメントがある場合は受け付けない。状態復元または押下送信時に `data-url` がある場合だけ登録・最終確認時刻を更新する。

## 6. v1.0 Phase 1による更新（2026-10-07）

- `identifier` はLikeボタンではなく集計対象のIDとし、同じIDを複数ウィジェットで共有できる。
- 最大長を100 Unicode code pointsへ拡張し、既存5テーブル用migrationを追加する。
- `data-identifier` 省略時は現在pathとDOM順から自動生成する。空属性はエラーとする。
- 設置先URLは `data-url`、canonical、`og:url`、現在URLの順に取得し、query・fragmentを除いてLike成立後だけ登録する。本節は上記「設置先URLと管理認証」の旧登録条件を更新する。
- 管理パスワードは12文字以上とし、`config/admin_credentials.json` には `password_hash()` の結果だけを保存する。
- 初回設定はlocalhostに限定する。ログイン成功時にセッションIDを更新し、CSRF検証、1分5回の試行制限、ログアウトを実装する。
