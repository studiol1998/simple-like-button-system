## 1. 動作環境・導入可否・検証実績

| PHP | 公式サポート | インストール可否・表示 |
| --- | --- | --- |
| 8.3以上 | 正式動作要件 | 他の必須条件を満たせば許可 |
| 8.1～8.2 | サポート対象外 | 現行インストーラーの通過を許容。非サポート警告は今後の実装予定であり、現在表示されるとは限らない |
| 8.0以下 | サポート対象外 | インストール不可 |

現行インストーラーの環境確認は8.1.0以上の判定である。8.3未満で通過しても公式サポートを意味しない。8.0以下の拒否を、古いPHPで必ず案内画面を描画できる保証とはしない。

PHP 8.1～8.2の警告表示は未実装としてDevelopmentPlanに記録する。

記録された自動検証環境はPHP 8.5.12（CLI・組み込みHTTPサーバー）である。8.1、8.2、8.3等の全環境で正常動作を確認した意味ではない。セキュリティサポート期間内で必要な修正の適用されたPHPを使用し、Web PHPとCLI PHPを別々に確認する。

診断用RuntimePolicyには8.3.36／8.4.27／8.5.12の系列別下限が記録されている。これは特定の修正に対する診断基準であり、最新版・全脆弱性対策・互換性を保証しない。ベンダーのバックポートは個別の公式根拠を確認する。

通常動作・インストーラーには統合されず、ZIPにも含まれない。正式サポート範囲や導入可否と同じ判定として扱わない。

PDO MySQL、JSON、セッション、およびMySQLまたはMariaDBのInnoDBが必要。設定・アーカイブ保存先への書き込み、ファイルロック・排他的作成、管理用PHP標準filesセッションの利用条件を確認する。公開領域外への分離設置は未検証・未対応であり、現時点の導入手順には含めない。

## 2. DB・ファイル・Webサーバーの準備

1. Pollyanna専用の空DBを作成する。既存アプリのDBへ新規インストールしない。
2. DBユーザーを作成または選択し、そのDBにCREATE、SELECT、INSERT、UPDATE、DELETEを許可する。ホスティング管理画面で個別指定が難しい場合は専用DBだけに「すべての権限」を付ける。サーバー全体への権限付与ではない。
3. DBホスト・ポート・DB名・ユーザー名・パスワードの5情報を控える。接頭辞が自動付与される環境では表示値をそのまま使用する。資格情報を公開文書・ログ・Gitへ保存しない。
4. 配布ZIPを展開し、標準のpollyanna/構成で配置する。設置名・場所を変更してもadmin/、api/、assets/等の相対構成を維持する。
5. PHP実行ユーザーがconfig/とlog/へ書き込めることを確認する。Apacheでは両方の.htaccessによる直接アクセス拒否が実際に機能することを確認する。Apache以外では同等のWebサーバー設定が必要。
6. 本番管理HTTPS、プロキシ、セッション保存条件を第4～5章に従って確認する。共有・ネットワークファイルシステムや異なるPHP実行方式ではロックの動作検証が必要であり、保護を無効にして導入しない。

インストーラーはDB本体・DBユーザーを作成しない。旧ベータ保存コードをそのまま公開領域へ配置しない。

LinuxではPHP実行ユーザーの所有権・書込権限とSELinuxを確認し、配置全体を777にしない。config/・log/のアクセス拒否は、Apacheでも.htaccessが有効な実設定で確認する。cron・Redis・外部API・追加ライブラリは必須ではない。

## 3. 新規インストール

画面は次の7段階である。

| 段階 | 確認内容 |
| --- | --- |
| ようこそ | DBとユーザー・権限・接続値の事前準備 |
| 環境確認 | PHP、PDO MySQL、JSON、セッション、必要ディレクトリ、アクセス保護等 |
| DB設定 | 接続情報の入力と接続確認。パスワードを再表示しない |
| 基本設定 | タイムゾーン、管理パスワードと確認、本体Origin・基準ドメイン、管理通信設定 |
| 実行確認 | 作成する設定・テーブル・管理接続先を確認。DBパスワード・秘密鍵を表示しない |
| インストール | 固定SQL、秘密鍵、設定・認証情報、完了状態の保存 |
| 完了 | install/全体を除去し、確認済み管理URLからログインする |

管理パスワードはSpecificationの規則に従う。秘密鍵はインストーラーが生成する。通常はWebインストーラーを使用し、設定テンプレートとSQLだけで管理認証・完了状態も揃うと誤解しない。

初期値は集計タイムゾーンAsia/Tokyo、システム状態（system_state）enabled（有効）、集計開始1,000件、バッチ500件、公開日本語、3回／24時間、件数非表示、件数表示時の更新5秒である。

テーマ等の生成値は現行のInstallerConfigと設定テンプレートを参照する。

手動設置ではconfig/config.example.phpを基にconfig/config.phpを作成し、設置ごとに異なる64文字の16進数をapp_secretへ設定してinstall/install.sqlを対象DBで実行する。ただし管理認証情報と完了状態も用意する必要がある。テンプレートとSQLだけでは導入を完了できず、通常はWebインストーラーを使用する。

### 3.1 管理環境の明示確認

基本設定で管理環境を必ず選択し、管理Originを確認する。初期選択は空欄で、
`localhost`やHTTPアクセスだけを理由に開発環境へ切り替えない。

- 本番環境：管理OriginはHTTPS必須である。パス・資格情報を含まないscheme・host・portを
  指定する。公開側`site_origin`を自動的に書き換えることはない。
- ローカル開発：明示選択に加え、直接ローカル開発である旨のチェックが必要である。
  実接続元とHostがループバックであり、転送ヘッダーがないことを既存ポリシーで検査する。
  LAN・公開・トンネル・プロキシ経由ではこの例外を使用しない。
- 管理パスはインストーラーの設置位置から自動算出し、改変したPOST値は拒否する。
  `/Pollyanna/`の大文字も保持する。リライトで実パスが異なる環境は別途確認が必要である。
- 確認画面でも管理環境・Origin・パスを表示し、実行直前に再検証する。
  選択情報がない旧ウィザードセッションは、基本設定へ戻って確認し直す。

`http://localhost/Pollyanna/`を使う場合、ローカル開発を選び、管理Originを
`http://localhost`、自動パスを`/Pollyanna/admin/`として確認する。生成結果は次の形である。

```php
'admin_security' => [
    'environment' => 'development',
    'origin' => 'http://localhost',
    'admin_path' => '/Pollyanna/admin/',
    'trusted_proxies' => [],
],
```

完了後に`install/`をアプリの配置場所から削除するか、公開領域外へ退避してから、
確認済みの管理Origin＋管理パスへ接続する。`install/`が残っている間は、従来の
設置状態判定に従って日英の削除案内だけを表示する。管理セッション・認証・設定保存は
開始しない。通信設定が不正でも案内を優先するが、管理操作を許可する例外ではない。

生成時の`trusted_proxies`は空である。TLS終端プロキシを使う本番環境では、管理アクセス前に
提供元の情報に基づく明示設定が必要である。プロキシヘッダーを自動的に信頼しない。
インストーラー全体のHTTPS強制や設置トークンは、この追加修正には含まない。

既にHTTPで設置済みの`config.php`は自動更新しない。既存DBへ再インストールせず、
後述の移行手順で管理設定だけを追加する。

設定生成は`src/InstallerConfig.php`にまとめ、インストーラーとテストが同じ処理を使う。
`config.example.php`との再帰的な項目・既定値比較も行う。具体的なOrigin・パスと秘密鍵は
設置に依存するため、テンプレートの省略値・プレースホルダーとの差をテスト側で明示する。
テンプレートの集中アクセス設定も、新規Web設置の既定値に合わせている。
既存の設定ファイルや保存済み設定は変更しない。

### 3.2 本体サイトと設置後の確認

本体Origin・基準ドメインの候補はアクセスURLから提示されるが、自動的に信用せず確認・修正する。サブドメイン許可は初期状態でON、localhost・IPでは無効となる。管理Originとは別の設定である。

install/全体を除去後、設定したパスワードでログインし、設定保存・再読み込み、動作テスト、手動識別子のボタン、件数取得・押下・上限を確認する。実サイトでの全機能検証が完了済みとは扱わない。

## 4. HTTPS・管理接続先・プロキシ

管理専用Originとパスの設定・省略時動作は第8章にも示す。HTTPのまま本番運用できる互換フォールバックはない。インストーラーが管理設定を生成することと、インストーラーの通信全体をHTTPS強制することは別である。本番の資格情報を入力する経路もHTTPSで準備する。

### 4.1 TLS終端プロキシ

TLSを終端するプロキシがある場合だけ、その接続元IPを`trusted_proxies`に列挙する。
完全一致のIPだけを許可し、CIDR・全許可・ヘッダーからの自動登録はない。
プロキシはHostを正しく保持し、`X-Forwarded-Proto`を利用者の入力から引き継がず
上書きして、単一の`https`または`http`を送る必要がある。

信頼済み接続のヘッダー欠落、空白、カンマ列、不正値は400で停止する。
未登録接続からの転送ヘッダーはHTTPSの証拠として使わない。
`Forwarded`、転送先Host・port・接続元IPヘッダーも判定には使わない。
ログイン試行制限用IPのプロキシ対応は、元資料で後続課題とされている。現在の確認状況はDevelopmentPlanの未解決事項を参照する。
プロキシがループバックでも、既存のローカル専用パスワード初期設定には使えない。

本番HTTPのGETは、固定したHTTPS管理URLへ302で転送し、元のクエリーを引き継がない。
HTTPのPOST等は403で拒否し、セッション開始・認証・設定保存を実行しない。
不正Hostは400、設定未確定は503である。POSTを受けてから転送して安全とは扱わない。

### 4.2 明示的なローカル開発例外

```php
'admin_security' => [
    'environment' => 'development',
    'origin' => 'http://localhost:8080',
    'admin_path' => '/pollyanna/admin/',
    'trusted_proxies' => [],
],
```

HTTP例外には明示した開発設定、ループバックOrigin/Host、ループバック接続のすべてが
必要である。転送ヘッダーやプロキシ設定がある場合はHTTP例外にしない。
XAMPP等も直接ローカル接続で使用し、LAN・トンネル・未申告プロキシで公開しない。
開発HTTPだけSecure属性を外し、それ以外のCookie保護を維持する。

## 5. 管理セッション・競合制御・保存失敗

### 5.1 最初に確認する保存方式・設定・権限

保証の対象は、適切な排他ロックが機能するローカルファイルシステムの標準`files`である。
平坦な`session.save_path`と`0;MODE;path`に対応する。階層分割保存、Redis、Memcached、
独自userハンドラー等は同じ保証を自動適用せず、管理認証を503で停止する。
別方式にはロック・失敗通知・strict modeの契約を確認したアダプターが必要である。
テスト用依存注入は信頼済みPHPコードだけの機構であり、HTTPや設定の解除機能ではない。

- PHP設定は`session.use_cookies=1`、`session.use_only_cookies=1`、
  `session.use_trans_sid=0`、`session.auto_start=0`が必要である。不適切な場合は安全側に停止する。
  `session.use_strict_mode=1`は開始前に有効化する。

- CookieはHost限定、管理パス限定、HttpOnly、SameSite=Strict、本番Secureである。

ネイティブハンドラーが成功を報告したことは確認するが、電源断後の永続性、fsync、
ストレージが黙ってデータを失う障害、NFS等の排他性までは証明しない。
GCや保存期間設定によってセッションがアプリの期限より早く消える場合もある。
実環境の権限・容量・ハンドラー・ファイルシステムは導入前の確認対象である。

導入前に保存先の権限・容量、ハンドラー、ファイルシステムと排他性を確認する。利用できない方式へ切り替えて保護を回避しない。内部処理の保証範囲は第5.4～5.5節を参照する。

### 5.2 503が発生したときの運用

通信設定・保存方式・開始／終了時の保存障害は同じ503になることがある。応答本文だけで一意に原因を断定せず、第9.4節の表に従って切り分ける。

- 出力と成功転送をバッファーし、終了時の保存確認が失敗した場合も503に置換する。
  設定ファイルの更新とセッション保存は一つのトランザクションではない。
  保存障害時に設定変更が既に完了している可能性はあるため、復旧後に状態を確認する。

保存失敗後は自動再送しない。サーバー側の保存方式・保存先の権限・容量を確認して復旧し、ログインし直した後に設定の反映状態を確認する。認証情報・秘密鍵を保持し、セッション一括削除・認証迂回で対処しない。復旧手順は第9.1・9.3節を参照する。設定・DBとセッションが単一トランザクションではないことの詳細は第5.5節に示す。

### 5.3 セッションの識別・認証状態・有効期限

- 名前は`pollyanna_admin_`とインストールID。インストーラーの名前とは分離する。
- 保存状態にもインストールIDを結び付ける。他の設置やインストーラーのSIDを
  管理Cookieへ渡しても、既存レコードを変更せず新しい管理セッションへ切り替える。
- IDを明示する場合は`instance_id`へ一意の32文字小文字16進数を設定する。
  同じ秘密鍵を複製して別設置を作る場合は、IDも衝突しないよう確認する。
- URL・POSTに専用セッション名が指定されている場合は拒否する。
- 認証時のID再生成とCSRF更新を維持し、認証時刻・最終管理アクセスを保存する。
  無操作30分・絶対8時間で失効する。公開APIのポーリングは延長しない。
- 時計の巻き戻り、不完全な認証状態、認証情報の変更でも失効する。
- ログアウトはセッション破棄とCookie失効。パスワード変更は現在の認証をクリアし、
  他セッションも次回アクセス時の資格情報スタンプ照合で失効する。

### 5.4 ネイティブロックと保存結果の確認

- PHPの標準`files`保存先を使い、ネイティブハンドラーをリクエスト内でラップする。
  永続PHP設定・保存先は変更しない。全状態の読み戻し・完全一致検査は廃止した。
  読み取り時に取得したネイティブロックを、認可・処理・最後の保存まで維持する。

旧処理は、`session_write_close()`による解放後に別要求が更新すると、読み戻した
セッション全体の比較に失敗していた。現在は開始時のreadと終了時のwrite/closeを
観測し、PHPの警告・例外とハンドラーの失敗戻り値を検出する。`session_write_close()`
単体の戻り値だけを成功判定にはしない。親`SessionHandler`へ処理を委譲するため、
標準ファイルハンドラーが取得したロックを保持したまま保存できる。

ログアウト・ID再生成では、待機要求が古いファイルを開いている場合にも古い認証を
読めないよう、ロック下で内容を空にしてからネイティブ削除を実行する。
失効した認証は再ログインなしで復活させず、CSRF検証も維持する。

### 5.5 同一SID・別SIDの競合と保証範囲

同一SIDの要求は直列待ちになる。長い集計等では待ち時間が生じるが、保存確認の
ためだけのロック再取得はしない。DBセッション方式は導入していない。

別SIDのパスワード変更は、資格情報を照合する時点が認可の境界である。変更後に照合する
旧セッションは拒否するが、変更前に認可済みの処理を途中キャンセルしない。
その処理が完了しても、次の要求では新しい資格情報で失効を確認する。

同一SIDの状態は直列化するが、別SIDによる設定ファイルの同時更新全般を原子的にする
変更ではない。セッション保存とDB・設定更新も一つのトランザクションではなく、
保存障害の503でも設定が既に変わっている場合がある。自動再送はしない。

## 6. ボタン設置・Origin設定・文言

標準的な埋め込み例。設置パスとURL、識別子を実際の対象へ変更する。

```html
<link rel="stylesheet" href="/pollyanna/assets/like.css?v=1">
<div data-pollyanna-like data-identifier="article-001" data-url="https://example.com/articles/001"></div>
<script defer src="/pollyanna/assets/like.js"></script>
```

CSS変更時はURLのv値を変更してキャッシュを更新する。集計を固定するには手動識別子を使う。自動識別子は例えば/a/news/article.htmlと/b/news/article.htmlの先頭で同じnews_article_001となり得る。空属性は省略とは異なる。複数ボタン共有やURL登録の規則はSpecificationを参照する。

外部Originで利用する場合は管理・運用設定で許可を追加する。Originはscheme・host・portだけを設定し、パスを含めない。canonical等が表示ページと別Originなら、URL登録側のOriginも許可が必要。削除は許可設定だけを消し、既存Like等を消さない。

file:、data:、sandboxによるnull Origin、独自schemeでの設置は対象外。WebViewではJavaScript・Fetch・DOM Storage／Website Data Storeの利用条件を確認する。プライベートモード、アプリ終了、データ削除、OSの整理等で状態を失い得る。SNSアプリごとの動作は実機確認が必要である。

公開文言はlang/widget.ja.jsonとlang/widget.en.jsonのsuccess_messagesで編集する。既存のlike01等のキーを保持して値を変更する。追加はlike07等の次の連番を両言語で揃え、選択中キーを削除・変更した場合は管理画面で選び直す。JSONにはコメントを書けない。管理用言語は公開言語と独立している。追加の管理言語はlang/admin.<言語コード>.jsonを用意する構成で、既存の日英キーとの整合を確認する。

### 6.1 設置場所とURL

標準設置例は/pollyanna/である。任意の名前・入れ子のサブディレクトリ、またはドキュメントルート直下へ中身を配置できる。admin/・api/・assets/・src/等の相対構成を保ち、既存ファイルとの衝突を避ける。ルート直下なら埋め込みURLを/assets/like.css・/assets/like.jsへ変更する。相対URLは埋め込み先HTMLの位置を基準に解決するため、ページごとに確認する。別Originから資材を読み込む場合は完全なHTTPS URLと適切なOrigin許可を用意する。CORSは利用者認証ではない。

cgi-bin/は全ファイルをCGIとして扱う環境があり、標準設置先として推奨しない。PHP実行とCSS・JavaScriptの静的配信を両立できる場合だけ検証する。ホスト・scheme・port変更時はOrigin設定を見直す。自動識別子はパスとDOM順に依存するため、ページ移動で集計対象が変わり得る。

### 6.2 管理画面の動作テスト

install/全体を除去してログインし、「動作テスト」（admin/?view=widget-test）を開く。2個のボタンで同一識別子の状態同期・件数更新・通常の押下上限を確認する。実API・DBを使用し、試験の押下は通常の統計・ランキングに含まれ、集中アクセス検知も適用される。管理画面の認証は公開API利用者の認証ではない。

固定識別子はPollyanna-test_01（ポリアンナテスト_01）。日本語が扱いにくい場合はadmin/widget-test-view.phpの$testIdentifier定義1か所を変更できる。別の集計対象となり、旧データは残る。最大100 Unicodeコードポイント、空白・制御文字とASCIIの「-」「_」以外の記号は禁止し、Unicode正規化は行わない。

中国語（测试01）、韓国語（테스트01）、アラビア語（اختبار01）、ヘブライ語（בדיקה01）、ロシア語（Тест01）、ギリシャ語（Δοκιμή01）も使用できる。受付可能な文字列とRTL表示品質は別である。識別子に方向制御文字を加えず、表示側のbdi・dir="auto"で方向を分離し、混在文字の表示・コピーを実ブラウザーで確認する。

### 6.3 集中アクセス検知の設定と解除

「集中アクセス検知」タブの上部で監視状況・有効ブロック・過去60日間の履歴を確認し、下部で設定する。履歴の1ページ件数は20（初期値）・50・80・100件で、選択はブラウザーに保存する。動作規則・期限切れ削除の条件と障害時の制約はSpecification第4.2～4.3節を参照する。

新規Web設置は検知ON・自動ブロックON。既存の保存済み設定は維持し、設定ファイルがない旧環境では検知ON・自動ブロックOFFとなる。検知OFFにすると自動ブロックもOFFで操作不可となる。検知ONへ戻しても自動ブロックは自動的にONにならない。検知ON・自動ブロックOFFで監視のみの運用ができる。旧設定の検知OFF・自動ブロックONは読込時に両方OFFへ正規化し、不整合のまま保存しない。

「いいね情報の取得」はstate.phpによる件数・押下状態の自動確認で、初期値は60秒に2,400回を超えると検知する。「いいねボタンの押下」はlike.phpへの送信で、初期値は60秒に240回を超えると検知する。監視時間と判定回数を設定し、初期値の自動ブロックでも履歴を確認してサイト規模・利用状況に合わせて調整する。

取得の想定モデルは、更新5秒なら1ボタン約12回／分、100ボタンが独立更新すると約1,200回／分、その2倍を2,400回とする。押下240回／分は平均4回／秒を想定した暫定基準である。いずれも実測値や攻撃判定の保証ではない。同一識別子のボタンは取得を共有し、表示ページ数・更新間隔・利用状況で通信量が変わる。共有IP・リバースプロキシでは誤ブロックの可能性がある。

解除は対象の管理用IDを確認し、確認操作を経て手動解除する。両APIのカウンターがリセットされる。検知・自動ブロックのOFFだけでは既存の有効ブロックを解除しない。期限切れ・手動解除後はその時点の設定で新規検知・再ブロックする。必要テーブル不足や管理側の読込失敗は画面の案内を確認し、公開側の検知障害ではログを確認する。検知障害は公開API全体の成功を保証しない。稼働確認とログ監視を行い、認証や安全機構を解除して復旧しない。

## 7. 運用・パスワード・バックアップ・アーカイブ

### 7.1 管理表示とパスワード

ログイン前のURL指定（language・theme）は、そのセッションの一時表示だけを変更する。ログイン失敗後や再読み込みでも保持するが、共有の管理設定は保存しない。ログイン成功時に一時表示を解除し、保存済み設定へ戻る。認証後の言語・テーマ選択は、CSRF検証付きPOSTで保存する。

新しく設定・変更するパスワードは、12 Unicodeコードポイント以上、UTF-8で72バイト以内、有効なUTF-8、NUL文字なしとする。文字数とバイト数は異なり、例えば一般的な日本語文字24個は72バイトである。前後空白はそのまま扱い、Unicode正規化や切り詰めは行わない。bcryptを明示し、コストはPHPの標準値を使用する。追加のmbstring拡張は不要である。

既存ハッシュは更新時にもログイン時にも自動変更しない。旧パスワードのログイン上限は従来の1024バイトを維持する。旧bcryptで72バイトを超えていた場合、先頭72バイト以降を区別できない。元の長さや末尾はハッシュから復元できないため、新しい規則へ移行するには明示的にパスワードを変更する。

「管理・運用設定」の「管理者パスワード変更」で、現在のパスワード、新しいパスワード、確認入力を送信する。認証・CSRF・現在のパスワード・新規則・確認一致がすべて必要である。試行はセッションごとに1分5回まで。失敗時は既存ハッシュを保持し、平文パスワードを再表示しない。

成功時は現在のセッションを終了し、他のログイン済みセッションも次の管理リクエストで失効する。新しいパスワードで再ログインする。ブラウザーの戻る・POST再送信では再変更できない。

セッションは認証情報の指紋を毎回確認する。この更新以前のセッションには指紋がないため、一度再ログインが必要である。認証JSONの形式は維持し、秘密鍵・DB接続情報は変更しない。無認証の再設定機能はない。configへのWebアクセス拒否を維持する。

### 7.2 バックアップとタイムゾーン変更

コード・DB・config設定と認証情報・秘密鍵・必要なlogアーカイブを対応する状態で安全にバックアップし、復元手順を準備する。バックアップをWeb公開領域やGitへ置かない。複製環境のセッション識別は第5章に従う。

タイムゾーン変更は通常の設定保存と別操作である。旧集計・公開件数のリセットを確認し、［はい］の後「現在のデータを集計中」「集計したデータを格納」の進捗を確認する。サイトAPIはメンテナンスとなり、未集計も含めて処理する。

日時入りlogフォルダーへの全CSV・metadata保存成功後だけリセットし、新タイムゾーンで0件から再開する。旧累計との合算はしない。

完了通知の保存先を確認する。アーカイブは自動削除されず、管理画面のダウンロード・削除機能もない。

容量を圧迫する場合は必要なローカルバックアップを取ったうえで、サーバー上の該当アーカイブを管理者が手動削除する。config/・log/の直接アクセス拒否を維持する。集約で失った粒度や削除したイベントをCSVから当然に復元できるとは扱わない。

## 8. 更新・移行

β-2配布ZIPは新規設置向けであり、一般利用者向けの旧版からの上書き更新・自動移行を正式保証しない。第8.1節はβ-1の既存設置を管理する所有者が、バックアップと隔離コピーでの確認を前提に管理通信設定を移行するための技術資料である。

全スキーマ・全旧版・データ移行の互換性を保証する更新手順ではない。第8.2節の注意と併せて読み、既存DBへの再インストールに転用しない。既存の技術手順は判断材料として維持する。

### 8.1 β-1からの管理通信設定移行

1. 既存コード・DB・設定のバックアップと復元手順を準備する。
2. 管理画面に使用するHTTPSのOrigin、設置パス、プロキシの有無を確認する。
3. **コードを置き換える前に**必要な`admin_security`設定を既存`config/config.php`へ
   追加する。この文書の作業では実設定を自動編集しない。
4. 隔離したコピーで更新・ログイン・Cookie・設定保存を確認してから反映する。
5. 新しい専用セッション名になるため、管理者は一度ログインし直す。
   この節の管理通信設定追加では、既存の管理認証情報・DB接続情報・app_secretを保持し、既存DB・集計データや公開ボタンのブラウザ保存領域を初期化する操作は行わない。更新全体の互換性や、通常稼働中にDB更新が発生しないことまでは保証しない。

設定を変更した際は、サーバーのOPcache等が古い設定を保持していないことも確認する。
この変更ではサーバーのキャッシュ・PHP設定を自動変更しない。

既存の`site_origin`が正しいHTTPSアドレスなら、設定項目がなくても本番用の
既定値で動く。インストールIDは既存`app_secret`から用途を分けて導出するため、
更新時に秘密鍵を再生成しない。設定の欠落・不正時にHTTPへ緩和しない。

既存`site_origin`がHTTPの場合、管理用HTTPSの`origin`を先に設定する。
設定しない場合、管理画面は503で停止する。これは公開APIのOriginを変更しない。
HTTP専用の本番環境への安全な互換フォールバックはない。HTTPSを用意するまで
更新を保留し、判断する。

```php
'admin_security' => [
    'environment' => 'production',
    'origin' => 'https://example.com',
    'admin_path' => '/pollyanna/admin/',
    'trusted_proxies' => [],
],
```

`origin`はscheme・host・portだけである。公開サイト設定を管理画面から変更する運用では、
管理接続先が巻き込まれないよう、この管理専用Originを明示することを推奨する。
省略時には既存`site_origin`を使用する。

`admin_path`は管理画面のURLパスである。省略時は、末尾が`/admin/index.php`である
`SCRIPT_NAME`から導出する。フロントコントローラー等で異なる値になる場合は
明示する。ドット・日本語を含む設置名も扱い、区切り・制御文字・親参照を
拒否してURLエンコードする。`HTTP_HOST`からOriginや転送先を作らない。
HTTPS/開発HTTPで認証を許可するURLは、設定した`admin_path`そのもの、またはその下の
`index.php`である。別名URL・異なるエンコード・誤ったCookie Pathは400で拒否し、
セッションを開始しない。リライトを使う場合も利用者の実URLと設定を合わせる。

### 8.2 旧ベータと過去のスキーマ更新

旧ベータは動作・移行検討の参考であり、そのまま本番配置しない。旧版には単純SHA-256のIPハッシュ、入力・HTTPメソッド・応答の検証不足、成功前提のJavaScript、仮の接続設定等の課題がある。現行のHMAC、匿名ブラウザ制限、Origin許可、トランザクション等と互換とみなさない。

過去の設計にはupgrade-identifier-urls.sql、upgrade-allowed-origins.sql等による追加手順がある。Origin表追加後に本体Origin・基準ドメイン等を保存する必要があり、未設定の間は公開Originを許可しない。

現在の配布ZIPは新規設置向けで、これらのSQLを同梱せず、既存環境への一括更新・データ移行を保証しない。現行スキーマと既存DBを隔離コピーで照合し、バックアップ・復元確認なしに再インストールしない。具体的な移行経路の未確認点はDevelopmentPlanに残す。

## 9. 障害時の復旧

### 9.1 管理設定の誤り

1. 管理画面へのアクセスを繰り返す前に、ファイル操作権限のある所有者が
   `config/config.php`をバックアップする。DBや認証ファイルは削除しない。
2. `admin_security.origin`を実際のHTTPS Originへ、`admin_path`をブラウザーで使う
   管理パスへ修正する。プロキシがある場合は実接続元IPと単一の上書きヘッダーを
   提供元資料で確認する。推測で全プロキシを許可しない。
3. 適切なセッションPHP設定と保存先の権限・容量を確認する。`app_secret`と
   `admin_credentials.json`は保持し、`development`へ変更して保護を解除しない。
4. PHP構文とOPcacheの反映を確認し、設定したHTTPS URLから接続する。
   通常の管理パスワードとCSRF検証を経てログインする。
5. 正しい値を確認できない場合は停止状態を維持する。復旧用の公開URL、認証省略、
   パスワード初期化、セッションファイルの一括削除は行わない。

### 9.2 インストーラーの同時実行・部分失敗

新規実行と完了処理の再試行は、config/.installer.lockの非ブロッキング排他ロックを使用する。取得後に状態を再確認し、新規実行はconfig/.installer-in-progressを排他的に作成する。ロックを取得できなければ書き込み前に停止する。既存のconfig・認証情報・秘密鍵を削除・上書きせず、DBテーブルの初期化もしない。

正常完了時だけ進行マーカーを削除し、ロックファイル自体は残して再利用する。異常終了・部分失敗時の進行マーカーは、時間経過だけで削除しない。完了マーカーがあっても進行マーカーが残れば部分状態として扱う。

以前の実行プロセスが停止したことを管理者が確認したうえで、保存済みconfig・認証情報と必要なDBテーブルを検証できる場合だけ「完了処理を再試行」を使う。

この復旧は完了マーカーの作成と進行マーカーの削除だけを行い、秘密鍵・認証情報を再生成しない。

configや認証情報が欠ける場合、完了マーカーが不正な場合は自動復旧せず停止する。既存成果物を保持して、バックアップとサーバー管理者による確認を行う。

ファイルロックと排他的ファイル作成が利用できるファイルシステムが必要である。共有・ネットワークファイルシステムや異なるPHP実行方式では、同時実行試験を行う。安全性を確認できない環境でロックなしの実行に切り替えない。cron・Redisは不要である。

### 9.3 集計・タイムゾーン変更・セッション保存の失敗

通常集計で例外が発生した場合、トランザクション中ならロールバックを試み、呼出元へエラーを返す。同一呼出し内の自動再試行は行わない。正常にロールバックされ保持された未集計イベントは、障害解消後の次回集計契機または管理画面の「今すぐ集計」で再処理できる。コミット結果が不明な障害で、必ずイベントが保持されるとは保証しない。

集計の再実行を目的としてLike送信を再送しない。Like受付と後続集計は別処理であり、集計が失敗してもLike自体は保存済みの場合がある。

タイムゾーン変更では旧タイムゾーン・稼働中データと中断状態を保持し、保護設定等の原因を直して管理画面の確認・再開経路を使用する。アーカイブが完成する前に集計テーブルを消去しない。エラーを避けるためにメンテナンス状態や進行マーカーを手動で無条件解除しない。

503の原因別切り分けは第9.4節を参照する。管理セッション保存障害の503では、設定変更がすでに完了している場合がある。自動再送せず、権限・容量・保存方式を復旧してから状態を確認する。ロックを無効化したりセッションファイルを一括削除したりしない。認証の迂回・公開の復旧URLは用意しない。

### 9.4 管理画面の503を切り分ける

HTTPステータスだけで原因を断定せず、所有者が実際のURL・応答本文・設定・サーバーのPHP診断を確認する。以下は現行admin/index.php、RequestSecurity、AdminSession、AdminSessionStoreの静的照合で確認できる範囲である。

新たな公開診断URLや原因別エラーコードを持つ実装は追加していない。

| 段階・応答 | 確認できる原因候補・限界 | 所有者が確認する箇所 |
| --- | --- | --- |
| install/の削除案内を表示する503 | 部分・完了状態でinstall/が残る場合。通信設定の検証・管理セッション開始より先に停止 | 完了／途中状態、実配置のinstall/全体、第3章と第9.2節。未完了を無理に完了扱いにしない |
| 「管理通信・セッション設定を確認してください。 / Administrator transport or session settings are unavailable.」の503 | 設定読込・管理Origin／パス等の検証失敗、またはセッション開始失敗を同じcatchで処理する。本文だけで通信と保存方式を特定できない | config.phpの構文・管理Origin／パス・秘密鍵／設置ID、次に第5.1節のPHP設定・files方式・保存先・権限・容量。第9.1節の順で確認 |

管理通信・セッションの上記catchには、原因別の専用error_log出力は確認できない。セッション処理は警告・例外・戻り値を捕捉して失敗判定するが、必ず原因別ログが出るとは案内しない。PHP／Webサーバー側に既存の診断が残るかは設定に依存する。

所有者が非公開の管理手段で確認し、ログ・設定・資格情報・SIDを公開しない。

アプリ以外のWebサーバーやプロキシが返した503、公開APIのメンテナンス503はこの表の管理画面処理と同一ではない。

切り分け時は応答元・対象URLも確認する。保存失敗後は自動再送せず、原因を復旧して反映済み設定を確認する。developmentへの切替、全プロキシ許可、認証回避、セッション一括削除を復旧策としない。

## 10. 導入後の確認と資料の版

新規設置後はinstall/除去、正しい管理URL・Cookie・ログイン、設定保存、公開API、上限、集計、保護されたCSV保存先を確認する。サブディレクトリと大文字の設置パス、プロキシ、ファイル保存条件は実際の配置で確認する。

既存試験の環境・範囲・限界は[DevelopmentPlan](DevelopmentPlan.md)第3章を参照する。模擬HTTPSやCLIでの成功は、本番TLS・Web PHP・ブラウザのCookie判定を検証したことにはならない。

配布物はREADME・ライセンス・設定テンプレート・必要コードを許可リストで収録し、テスト・実設定・認証情報・セッション・ログを含めない。現在のdocs/はZIP対象外で、READMEから参照する資料とコードの版を揃える必要がある。本統合案の承認前にはREADMEの参照先を切り替えない。

### 10.1 ZIPを変更しない現行方針と公開時のリンク切替

現行tools/build-release.ps1の許可リストは37ファイルで、README.md・README.en.md・install/readme.phpを含む一方、docs/を明示的に除外する。本工程ではZIP・許可リスト・READMEを変更しない。

GitHubで閲覧するアプリREADMEとZIP内のREADMEは同じ元ファイルから配布される。アプリREADMEにdocs/Installation.mdという相対リンクだけを置くと、GitHubでは存在してもZIPの展開先にはdocs/がなく参照できない。

両方から到達させる利用者向け詳細資料は、対象コードと対応を確認したGitHub上の文書への絶対URLを使う。リポジトリ内だけの入口は相対リンクを使える。

コードと資料の版を固定できる場合、絶対URLのblob/mainを、実在と対応コミットを確認したリリースタグまたはコミット参照へ置き換える。

未作成タグを有効な参照として使わない。

mainを使う場合は資料が先行更新され得ることを明示し、公開時に到達性を確認する。本工程ではGitHubの公開状態・URL到達性を確認していない。

現在の旧リンクは対象資料をまだ削除していないため、ローカルの再編だけで直ちに切れているわけではない。

旧資料を公開対象から外す前に新リンクの公開・到達を確認する。

install/readme.phpは同梱READMEをtext/plainで表示するためリンクはブラウザ内でクリック可能とは限らないが、絶対URLをコピーして参照できる。install/除去後も同梱README自体を手元で参照できる必要がある。

READMEを変更したら検証済みZIP内のREADMEとの差が生じるため、配布物の版・内容・ハッシュの整合を別工程で再確認する。

既存ZIPをこの工程で上書きせず、新たな配布物の生成・検証は別の明示指示で行う。
