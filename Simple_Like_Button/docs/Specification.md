# Pollyanna 現行仕様

制作者：にくきぅSYSTEMs（Nikukiu-SYSTEMs）

状態：公開済みプレリリースv1.0.0-beta2の承認済み文書。従来の日本語開発基準3文書と採用済み設計を統合した現行仕様である。

適用対象はv1.0.0-beta2である。文書固有の版番号は追加しない。公開時点の内容はv1.0.0-beta2タグで、公開後の文書校正はGitコミットで管理する。共通の版管理方針は[DevelopmentPlan](DevelopmentPlan.md)第1.1節を参照する。

## 1. 適用範囲と文書の役割

Pollyannaは、サイトへ軽量に埋め込む自己ホスト型のいいねボタンシステムである。identifier（識別子）はボタン自体ではなく、いいねの集計対象を区別する値であり、管理画面の「いいね ID」「Like ID」も同じ値を指す。

本書は現行の確定した動作規則を扱う。実装・検証の状態、仕様とコードの相違、将来の判断は[開発計画](DevelopmentPlan.md)、設置と復旧の具体的操作は[設置・運用資料](Installation.md)を正本とする。未解決事項は本書で補完しない。β-2は正式版ではなく、実サイト試験前のプレリリースである。

正式動作要件はPHP 8.3以上であり、8.2以下は公式サポート対象外。インストールを許可する範囲と検証実績は別である。詳細はInstallationの第1章を参照する。

## 2. 識別子と設置先URL

### 2.1 識別子

- UTF-8、DBではutf8mb4を使用し、最大100 Unicodeコードポイントとする。
- Unicode文字・数字・句読点・記号を扱い、ASCII記号はハイフンとアンダースコアを許可する。空白、制御文字、その他のASCII記号は受け付けない。
- data-identifierを明示すると手動識別子、属性を省略すると現在のパスとDOM順からの自動生成となる。空属性は設定エラーである。
- 同じ対象に同じ識別子を指定して複数ウィジェットで共有できる。異なる集計対象には異なる値を指定する。
- 自動生成はページ間の一意性を保証しない。集計を固定するときは手動識別子を使用する。

### 2.2 設置先URL

URL候補はdata-url、canonical、og:url、現在URLの順とし、query・fragmentを除去する。HTTP/HTTPSの正規化したURLをLike成立後だけ登録する。状態取得だけでは登録しない。

同じ識別子に複数URLを保存でき、URLのSHA-256と識別子で対応を管理し、初回・最終確認時刻を持つ。資格情報を含むURLは受け付けない。

リクエストのOriginと登録URLのOriginはそれぞれ許可対象である必要があるが、両者の完全一致は要求しない。URLのOriginが不許可でも成立済みLikeは取り消さず、URL登録を見送りサーバーログへ記録する。

ページタイトル・リファラーは収集しない。

## 3. ボタン・押下状態・公開件数

押下はサーバーの受付成功後に未押下から押下後表示へ変える。通信失敗・メンテナンス・上限を通常成功と区別する。公開JavaScriptは初期状態を取得し、押下結果を反映する。

ランダムな匿名ブラウザトークンをlocalStorageに保存し、サーバーにはそのHMAC値を保存する。押下済み識別子もブラウザ側に保持し、集計による個別イベント削除後の表示復元を補助する。

サーバー側は未集計イベントを状態確認に用い、確認できた押下状態をブラウザにも反映する。状態表示のためだけにブラウザ別履歴をサーバーへ長期保存しない。

localStorage消去・ブラウザや保存領域の変更では別の匿名利用者として扱われ得る。ブラウザ識別は本人認証ではない。同じ識別子でも異なるOriginのlocalStorageは分離されるため、状態や制限枠の共有を保証しない。

公開件数は既定で非表示。有効時は集計済み累計と未集計イベントを合算し、集計の前後で件数を失わない。非表示時は公開APIから件数を返さず、初回状態確認だけを行う。

公開件数の更新間隔は5秒（初期値）、10秒、30秒、60秒、0秒（更新なし）。同一ページ・同一識別子の複数ボタンは初期取得と更新タイマーを共有し、Like成功結果を直ちに同期する。

タブ非表示中・メンテナンス中は停止し、通信失敗時は最大60秒の指数バックオフを使う。like.jsの二重初期化を防ぐ。

日英表示、成功メッセージ選択、ハート・ダイヤ・スペード・クラブ・星・音符の固定プリセット、未押下・押下後の記号色、件数色を備える。未押下色は濃い灰色#666666または薄い灰色#ccccccから選び、押下後の色は#RRGGBBで指定する。表示設定がない場合の既定はハート・#666666・#e53955である。設定と文言編集の手順はInstallation第6章を参照する。

## 4. 押下制限と異常アクセス対策

### 4.1 作品別・匿名ブラウザ別の押下上限

identifierと匿名ブラウザの組ごとに直近24時間の受付回数を判定し、1～5回、初期値3回とする。IPハッシュをこの上限の本人判定に使わない。個別集計イベントと上限判定用記録を分離し、同じ識別子・ブラウザからの次回押下時に期限切れ判定記録を削除する。同時押下でも上限を越えて保存しないため、ロックとトランザクションを用いる。

### 4.2 集中アクセス検知

公開APIのアクセス監視・一時遮断は作品別押下上限とは独立した機能である。検知処理は接続元IPを処理中に利用し、IP由来のHMACを扱う。生IPを処理に利用することと、生IPをPollyannaの永続記録として保存することは別である。このため、「IPによる作品別制限をしない」を「IPに関係する遮断がない」と読み替えない。

管理側には監視・ブロック・解除・履歴の機能がある。IPハッシュ値そのものは通常の管理画面の表示項目にしない方針を引き継ぐ。

静的に確認したapi/bootstrap.phpではREMOTE_ADDRを取得してAccessProtectionService::ipHashへ渡す。同クラスはIPをinet_ptonで変換し、設置秘密鍵から用途分離した鍵によるHMAC-SHA-256を生成する。確認したDB書き込み経路では、アクセス検知バケットと一時ブロックにIPハッシュを保存する。履歴の現行スキーマには生IP・ip_hash列はない。

この確認は当該コード経路とSQLに限り、すべてのログ・外部保存先を実環境で監査した結果ではない。

β-2では、現行api/bootstrap.phpの異常アクセス検知に限るfail-openを維持する。必要なアクセス検知テーブルを利用できない場合や検知処理の例外時には、一般化したerror_logを出してこの検知を継続せず公開API処理へ戻る経路がある。

接続元IPをHMAC化できない場合も例外経路に入り得る。

検知失敗は公開API全体の成功を保証せず、後続のDB処理等が失敗する場合もある。Origin検証・入力検証・作品別の押下上限等は独立して実施され、検知失敗によって解除されない。

一方、検知不能時には既存の一時遮断も機能しない可能性がある。検知処理の例外発生時でも、コミット後のロック解放失敗等により検知用DB更新が既にコミットされている場合がある。

fail-openはβ-2の現行動作を維持する判断であり、恒久的なセキュリティ方針として確定するものではない。

保存先はアクセス検知バケット、一時ブロック、履歴に分かれる。旧設計の「調査用IPハッシュは60日」を全保存先に一律適用する説明は採用しない。

保持対象・期限・削除契機の整理はDevelopmentPlan第4章の確認事項とする。15日・30日・60日の選択機能は現行機能ではない。

### 4.3 集中アクセス検知の計測・遮断規則

以下はβ-2の現行コードとREADMEに記録された動作規則である。第4.2節の障害時の制約、および保存先別の保持対象・削除条件を再確認する課題は維持する。

| 対象API | 初期監視時間 | 初期判定回数 |
| --- | --- | --- |
| state.php（いいね情報の取得） | 60秒 | 2,400回 |
| like.php（いいね送信） | 60秒 | 240回 |

接続元ごと・APIごとに直近期間を1秒単位のバケットで計測し、指定回数を超えた場合に検知する。監視時間は10～3,600秒、判定回数は1～1,000,000回。検知のみの運用では、同じ接続元・APIの直近期間に検知記録がある間、履歴の重複を抑える。

正常なOPTIONSは計測せず、不正入力・不許可Origin・不正なOPTIONSは計測する。不許可Originの403、正常なOPTIONSの204はブロック中も維持する。許可Originでブロック中の場合はCORSヘッダー付き429とRetry-Afterを返す。作品別・匿名ブラウザ別の押下上限による429とは別である。遮断対象は両公開APIだけであり、管理画面・通常ページ閲覧は遮断しない。

自動ブロックは開始から48時間で失効する。期限切れまたは手動解除後に再び検知条件を超えると、新しい履歴と48時間ブロックを作成する。期間延長や永久ブロックは行わない。手動解除時は両APIの判定カウンターをリセットする。検知OFFは新規検知とカウンター保持、自動ブロックOFFは新規自動ブロックを停止するが、既存の有効ブロックは期限まで継続し、切替で期限を延長しない。第4.2節のとおり、検知不能時には既存ブロックも機能しない可能性がある。

IPはREMOTE_ADDRから取得し、転送ヘッダーは使わない。既存app_secretから用途分離したHMACを短期判定・ブロック管理に使い、履歴にはIP・IPハッシュを保存しない。共有回線・リバースプロキシでは利用者のアクセスが合算され、誤ブロックする可能性がある。これはPHP・DBへ到達する前の大規模攻撃を遮断するネットワーク防御ではない。

期限切れデータの削除は次の公開API判定または認証済み管理画面アクセス時に行う。正常なOPTIONSも計測せず削除処理を行う。無アクセス中は物理削除が遅れるが、期限切れブロックは次の判定で適用しない。現行コードの履歴は検知日時から60日で削除対象となる。この条件を全IP関連保存先へ一律適用したり、将来の保持期間選択機能の実装済み保証としたりしない。cronは不要である。判定・削除・解除はDB単位の短い排他ロックで直列化する。

内部保存・期限判定はUTC、管理表示は集計タイムゾーンと各日時に対応する略称（夏時間を含む）を使う。タイムゾーン変更は検知履歴・ブロック期限・検知設定を変更しない。設定と解除の操作はInstallation第6.3節を参照する。

## 5. データ構造・集計・保持

### 5.1 データ最小化と構造

時刻はUTCで保存し、集計時に設定タイムゾーンへ振り分ける。Pollyanna自身は、生IPを永続記録として保存せず、検知用にはIP由来のHMACを使用する方針とする。接続元IPは第4.2節の処理で利用するため、「IPを一切取得しない」という意味ではない。

ページタイトル、リファラー、生ブラウザトークン、User-Agentを収集・保存しない方針は維持する。秘密鍵は設定ファイルに保持し、DBへ保存しない。

Webサーバー・リバースプロキシ・ホスティング等のアクセスログはPollyanna自身の保存とは別であり、生IPが記録される可能性がある。それらの設定・保存内容・保持期間は管理者による確認対象で、本仕様が保存を停止したり未確認の記録不存在を保証したりするものではない。IP関連記録の保持期間・削除条件の整理はDevelopmentPlan第4章に残す。

現在の固定SQLにあるテーブルは次の10種類である。SQL型・索引の詳細は[初期スキーマ](../install/install.sql)を参照する。

| テーブル | 役割・主要な対応 |
| --- | --- |
| pollyanna_likes | 未集計イベント。id、identifier、client_hash、created_at。識別子・日時とブラウザハッシュ・日時の索引 |
| pollyanna_rate_limit_events | 押下制限用の短期イベント。識別子・ブラウザハッシュ・日時の索引 |
| pollyanna_lifetime_totals | 識別子ごとの累計 |
| pollyanna_period_aggregates | day/month/year、開始日、識別子、件数。期間種別・開始日・識別子の複合主キー |
| pollyanna_hourly_aggregates | サイト全体の月初日・0～23時・件数。月初日と時刻区分の複合主キー |
| pollyanna_identifier_urls | 識別子・URLハッシュ・正規化URL・初回／最終確認日時 |
| pollyanna_allowed_origins | scheme・host・実効port・サブドメイン許可。scheme・host・portの一意制約 |
| pollyanna_access_buckets | IPハッシュ・API・時刻区分ごとの検知用件数 |
| pollyanna_access_blocks | IPハッシュに対する一時ブロックと期限・履歴対応 |
| pollyanna_access_history | 検知日時・件数・ブロックと解除の履歴。現行SQLにはip_hash列はない |

旧Reviewの汎用settingsテーブル案を、実在するテーブルとしては採用しない。運用設定はconfig配下の設定・保存済みJSON等を使用する。

### 5.2 集計の起動と原子性

個別Likeをイベントとして記録し、集計値へ反映してから個別イベントを削除する。自動集計開始件数は1,000（初期値）、2,000、4,000、6,000、8,000、10,000件から選択する。しきい値に達した時、または管理画面アクセス時に処理する。

未到達分を時間経過だけで処理するcron等の定期実行は設けない。どちらの起動もなければ未集計のまま保持する。

通常バッチの既定上限は500件であり、起動しきい値・日別行数上限とは別の値である。当面、管理画面からこのバッチ上限を変更しない。

取得・集計値更新・処理済みイベント削除を同一の短いDBトランザクションで行う。例外発生時にトランザクション中であればロールバックを試み、呼出元へエラーを返す。

同一呼出し内の自動再試行は行わない。正常にロールバックされ保持された未集計イベントは、障害解消後の次回集計契機または管理画面の「今すぐ集計」で再処理できる。

通信断等でコミット結果が不明な場合に、必ずイベントが保持されるとは保証しない。

DB単位のロックで集計同士の並行実行を防ぐ。削除と集計が同時にコミットすることが二重加算・記録消失防止の根拠となる。

### 5.3 長期保持と時間帯別集計

長期統計は累計・期間別・時間帯別の三種類を基本とする。

#### 確定した設計方針

- 日別は最大5年かつ50,000行を基本とし、保持期間または件数の条件を超える古い分を月別へまとめる。直近3年程度の詳細需要に余裕を持たせるため5年を採用した。件数条件が先に来れば5年より前に詳細を失うため、常に5年分を残す保証ではない。
- β-2の日別上限50,000行は固定値。v1.0.0も維持する方針で、管理画面からの変更は現行機能ではない。
- 月別から年別へ集約し、年別は保持する。月別の5年保持という元設計を維持するが、起算点は次の確認事項と分けて扱う。
- 時間帯別はサイト全体を月別・1時間区分で既存バッチ中に集計し、件数のある区分だけを保存、直近24か月を保持する。識別子別の時間帯集計を提供する構造ではない。

#### 実装上の未確認事項・元設計との相違

50,000行の適用範囲が全体か識別子別か、50,001行目の生成と集約開始の関係、バッチでの超過解消回数は未確定の確認事項である。コードの静的読み取りを設計上の保証へ置き換えず、[DevelopmentPlan](DevelopmentPlan.md)第4章の観測と再検証事項として管理する。

DevelopmentPlan第3.1節に記録した過去の50,001行試験では、識別子数・投入方法・バッチ条件等が未確認である。現行の50,002識別子を用いるSQLite試験は別条件の限定試験で、上限の設計上の適用範囲や実MySQLでの超過解消条件を確定しない。詳細はDevelopmentPlan第3.1・第4章を参照する。

月別保持については、「月別化してから5年」という元設計とperiod_startを用いる実装に起算点の相違がある。

起算点を独断で確定せず、実際の月別保持期間を保証しない。保持条件の再評価を行うことと、その結果として上限変更・保持期間選択等を実装することは別である。

集約済みの個別イベントからの再計算や、月別・年別化したデータを日別へ戻すことはできない。時間帯別は実装済みだが、正式公開版への採用判断が試用後として残っている。実装済みと正式採用判断は別である。

## 6. 管理画面と設定

現行コードのタブはDashboard、個別詳細、管理・運用設定、サイト表示設定、集中アクセス検知の5区分である。旧設計の「設定」は管理・運用とサイト表示に分かれている。古い資料の「認証未実装」「localhost限定のテスト画面」を本番画面の現状としない。

| 項目 | 現行の機能・制約 |
| --- | --- |
| Dashboard | 総数、集計済み・未集計、識別子数、直近7日・当月を含む12か月・当月0～23時。日別等は未集計分と整合する集計値を扱う |
| 個別詳細 | ID検索、期間・粒度、累計・期間件数、推移と表、20件単位のページ送り、設置URL。時間帯別はサイト全体の別枠 |
| 今すぐ集計 | 通常1バッチを実行。グラフの読み直しとは別の操作。失敗時のイベント保持と再実行条件は第5.2節に従う |
| 保存区分 | 管理・運用とサイト表示を区分して保存。タイムゾーン変更は独立操作 |
| 表示言語・テーマ | 管理と公開の言語は独立。9テーマ：システム、ライト、ダーク、グリーン、ブルー、オレンジ、レッド、パープル、モノクロ |
| 集中アクセス検知 | 監視条件、検知履歴、一時遮断、解除を扱う |

0件と取得失敗、保存されていない期間と実測0件、集約済み粒度と日別詳細を区別する。グラフと表を併設して色やマウス操作だけに依存しないという設計方針を引き継ぐ。旧画面案の配置寸法・将来の割合表示案の採用状態はDevelopmentPlanで管理する。

管理パスワードは新規設定・変更時に12 Unicodeコードポイント以上、UTF-8で72バイト以内、有効UTF-8、NULなし。bcryptを明示しPHP標準コストでハッシュ化する。前後空白を保持し、正規化・切り詰めを行わない。

既存ハッシュは自動更新しない。変更には認証・CSRF・現在のパスワード・確認一致が必要で、成功後は再ログインを必要とする。詳しい旧パスワードの制限・手順はInstallation第7章を参照する。

## 7. インストーラーの動作契約

日本語・英語に対応し、ようこそ、環境確認、DB設定、基本設定、実行確認、インストール、完了の7段階とする。DB自体やDBユーザーは作成しない。専用空DBへ固定SQLでテーブルを作成し、64桁16進の暗号学的乱数による秘密鍵、設定、管理認証情報、完了マーカーを保存する。

セッション・CSRFを使用し、DB接続値をSQLへ連結しない。パスワード・秘密鍵を確認画面やログへ出さない。新規実行と完了復旧はファイルロック下で状態を再確認し、進行マーカー・成果物を排他的に新規作成する。

既存設定や認証情報を上書きせず、DBテーブルを初期化しない。完了済み環境の一般的な再実行・上書き修復は禁止する。

失敗後は作成済み成果物と進行状態を保持する。復旧は停止確認と成果物検証後の完了処理だけを対象とする。詳細はInstallation第9章を正本とする。

install/全体が残る間、部分・完了状態の管理画面はログイン前に削除案内で停止し、管理セッションや操作を開始しない。index.phpだけの削除・画面操作では解除しない。通信設定の不備より削除案内を優先しても、認証迂回の例外にはしない。

管理Originと管理パスは確認・検証して生成する。本番管理OriginはHTTPS。ローカルHTTPは明示選択・直接ループバック確認を必要とする。ただしインストーラー全体のHTTPS強制や設置トークンまで実装済みという意味ではない。

## 8. Origin・CORS・管理セキュリティ

公開state/like APIはOrigin必須。欠落、null、不正、未許可は403とし、Refererへフォールバックしない。このOrigin制限を管理画面・インストーラーへ一律適用しない。

本体はsite_origin、site_base_domain、site_base_domain_include_subdomains、外部は許可テーブルで管理する。scheme・実効portは一致必須、hostは完全一致か、許可時に「.＋許可host」で終わるものだけを認める。localhost・IPではサブドメイン許可を適用しない。単純な部分一致を使わない。

OriginはHTTP/HTTPSのscheme・host・portだけを受け付け、scheme・DNS hostを小文字化し既定portを省略する。path、query、fragment、ユーザー情報を拒否する。許可された外部Originへ具体的なAccess-Control-Allow-OriginとVary: Originを返し、ワイルドカードやcredentialsは使わない。

外部OriginのJSON POSTはpreflight対象。OPTIONSでもOriginを照合し、要求methodがPOST、要求headerがContent-Typeだけなら204。実POSTでも再検証する。管理画面で外部Originを削除しても、Like・集計・識別子・URL履歴を削除しない。

Origin許可はBot認証ではなく、Origin偽装、許可サイトのXSS・サブドメイン乗っ取り、localStorage消去や分散アクセスを防ぐものではない。入力検証・押下制限・異常アクセス対策・トランザクションを引き続き必要とする。

管理認証は本番HTTPS、セッションID更新、CSRF、試行制限、認証状態失効を使用する。管理Cookie・保存方式・期限・競合時の保証範囲・HTTP拒否は[Installation](Installation.md)第4～5章を詳細の正本とする。公開ポーリングで管理認証を延長しない。

## 9. タイムゾーン変更とCSV

タイムゾーン変更は運用地域の変更として扱い、過去集計を新タイムゾーンへ組み替えない。確認後に未集計も確定し、日時入りlog/フォルダーへ退避してから稼働中の集計をリセットする。公開件数も0から再開し、旧累計と合算しない。

変更中は公開APIをメンテナンスにし、中断状態を保存する。

保存物はmetadata.json、lifetime_totals.csv、period_aggregates.csv、hourly_aggregates.csv。変更日時・変更前後のタイムゾーン等を記録する。CSVはfputcsvで生成し、数式として扱われ得るidentifier（識別子）に先頭アポストロフィを付ける。アーカイブ失敗時に旧タイムゾーン・稼働中データを維持し、格納が完成する前に消去しない。

自動削除期限、管理画面のアーカイブダウンロード・削除機能は設けない。汎用の統計CSVダウンロード画面まで実装済みとはしない。運用操作・バックアップはInstallation第7・9章、試験結果はDevelopmentPlan第3章を参照する。

## 10. 確定した制約

- 自動識別子は異なるページ間で衝突し得る。
- localStorageはOrigin・ブラウザ・プロファイル・WebViewデータ領域等で分離される。消去後の本人同一性は保証しない。
- HTTP/HTTPSのWebページが設置対象。file:、data:、独自scheme、null Originは許可しない。
- WebViewのJavaScript・Fetch・localStorage利用可否や永続性はアプリ設定次第。個別アプリの正式対応・最低版は未確定であり、実機検証を保証しない。
- 公開領域外への分離インストールは現時点で未検証・未対応。
- β-2の配布は新規インストール向けで、旧ベータの無条件更新やデータ互換を保証しない。
- PHP 8.3以上という正式要件は、全バージョンの検証完了や修正未適用版の安全性を意味しない。
