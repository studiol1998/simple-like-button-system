# 管理HTTPS・セッション移行（第2工程A）

今回の変更は管理画面だけに適用します。公開API、インストーラー、DBスキーマ、
ログイン試行制限は変更しません。インストーラーのHTTPS・セッション強化は未実装です。
実サーバーへの反映・配布ZIPへの組み込みは、この工程では行っていません。

## 新規インストールの管理環境設定

基本設定で管理環境を必ず選択し、管理Originを確認します。初期選択は空欄で、
`localhost`やHTTPアクセスだけを理由に開発環境へ切り替えません。

- 本番環境：管理OriginはHTTPS必須です。パス・資格情報を含まないscheme・host・portを
  指定します。公開側`site_origin`を自動的に書き換えることはありません。
- ローカル開発：明示選択に加え、直接ローカル開発である旨のチェックが必要です。
  実接続元とHostがループバックであり、転送ヘッダーがないことを既存ポリシーで検査します。
  LAN・公開・トンネル・プロキシ経由ではこの例外を使用しません。
- 管理パスはインストーラーの設置位置から自動算出し、改変したPOST値は拒否します。
  `/Pollyanna/`の大文字も保持します。リライトで実パスが異なる環境は別途確認が必要です。
- 確認画面でも管理環境・Origin・パスを表示し、実行直前に再検証します。
  選択情報がない旧ウィザードセッションは、基本設定へ戻って確認し直してください。

`http://localhost/Pollyanna/`を使う場合、ローカル開発を選び、管理Originを
`http://localhost`、自動パスを`/Pollyanna/admin/`として確認します。生成結果は次の形です。

```php
'admin_security' => [
    'environment' => 'development',
    'origin' => 'http://localhost',
    'admin_path' => '/Pollyanna/admin/',
    'trusted_proxies' => [],
],
```

完了後に`install/`をアプリの配置場所から削除するか、公開領域外へ退避してから、
確認済みの管理Origin＋管理パスへ接続します。`install/`が残っている間は、従来の
設置状態判定に従って日英の削除案内だけを表示します。管理セッション・認証・設定保存は
開始しません。通信設定が不正でも案内を優先しますが、管理操作を許可する例外ではありません。

生成時の`trusted_proxies`は空です。TLS終端プロキシを使う本番環境では、管理アクセス前に
提供元の情報に基づく明示設定が必要です。プロキシヘッダーを自動的に信頼しません。
インストーラー全体のHTTPS強制や設置トークンは、この追加修正には含みません。

既にHTTPで設置済みの`config.php`は自動更新しません。既存DBへ再インストールせず、
後述の移行手順で管理設定だけを追加してください。

設定生成は`src/InstallerConfig.php`にまとめ、インストーラーとテストが同じ処理を使います。
`config.example.php`との再帰的な項目・既定値比較も行います。具体的なOrigin・パスと秘密鍵は
設置に依存するため、テンプレートの省略値・プレースホルダーとの差をテスト側で明示します。
テンプレートの集中アクセス設定も、新規Web設置の既定値に合わせています。
既存の設定ファイルや保存済み設定は変更しません。

## β1からの移行順序

1. 既存コード・DB・設定のバックアップと復元手順を準備します。
2. 管理画面に使用するHTTPSのOrigin、設置パス、プロキシの有無を確認します。
3. **コードを置き換える前に**必要な`admin_security`設定を既存`config/config.php`へ
   追加します。この文書の作業では実設定を自動編集しません。
4. 隔離したコピーで更新・ログイン・Cookie・設定保存を確認してから反映します。
5. 新しい専用セッション名になるため、管理者は一度ログインし直します。
   パスワード、DB、集計、公開ボタンの保存状態は変更しません。

設定を変更した際は、サーバーのOPcache等が古い設定を保持していないことも確認します。
この変更ではサーバーのキャッシュ・PHP設定を自動変更しません。

既存の`site_origin`が正しいHTTPSアドレスなら、設定項目がなくても本番用の
既定値で動きます。インストールIDは既存`app_secret`から用途を分けて導出するため、
更新時に秘密鍵を再生成しないでください。設定の欠落・不正時にHTTPへ緩和しません。

既存`site_origin`がHTTPの場合、管理用HTTPSの`origin`を先に設定します。
設定しない場合、管理画面は503で停止します。これは公開APIのOriginを変更しません。
HTTP専用の本番環境への安全な互換フォールバックはありません。HTTPSを用意するまで
更新を保留し、判断してください。

```php
'admin_security' => [
    'environment' => 'production',
    'origin' => 'https://example.com',
    'admin_path' => '/pollyanna/admin/',
    'trusted_proxies' => [],
],
```

`origin`はscheme・host・portだけです。公開サイト設定を管理画面から変更する運用では、
管理接続先が巻き込まれないよう、この管理専用Originを明示することを推奨します。
省略時には既存`site_origin`を使用します。

`admin_path`は管理画面のURLパスです。省略時は、末尾が`/admin/index.php`である
`SCRIPT_NAME`から導出します。フロントコントローラー等で異なる値になる場合は
明示してください。ドット・日本語を含む設置名も扱い、区切り・制御文字・親参照を
拒否してURLエンコードします。`HTTP_HOST`からOriginや転送先を作りません。
HTTPS/開発HTTPで認証を許可するURLは、設定した`admin_path`そのもの、またはその下の
`index.php`です。別名URL・異なるエンコード・誤ったCookie Pathは400で拒否し、
セッションを開始しません。リライトを使う場合も利用者の実URLと設定を合わせてください。

## プロキシ

TLSを終端するプロキシがある場合だけ、その接続元IPを`trusted_proxies`に列挙します。
完全一致のIPだけを許可し、CIDR・全許可・ヘッダーからの自動登録はありません。
プロキシはHostを正しく保持し、`X-Forwarded-Proto`を利用者の入力から引き継がず
上書きして、単一の`https`または`http`を送る必要があります。

信頼済み接続のヘッダー欠落、空白、カンマ列、不正値は400で停止します。
未登録接続からの転送ヘッダーはHTTPSの証拠として使いません。
`Forwarded`、転送先Host・port・接続元IPヘッダーも判定には使いません。
ログイン試行制限用のIPの扱いは第2工程B以降の課題です。
プロキシがループバックでも、既存のローカル専用パスワード初期設定には使えません。

本番HTTPのGETは、固定したHTTPS管理URLへ302で転送し、元のクエリーを引き継ぎません。
HTTPのPOST等は403で拒否し、セッション開始・認証・設定保存を実行しません。
不正Hostは400、設定未確定は503です。POSTを受けてから転送して安全とは扱いません。

## ローカル開発

```php
'admin_security' => [
    'environment' => 'development',
    'origin' => 'http://localhost:8080',
    'admin_path' => '/pollyanna/admin/',
    'trusted_proxies' => [],
],
```

HTTP例外には明示した開発設定、ループバックOrigin/Host、ループバック接続のすべてが
必要です。転送ヘッダーやプロキシ設定がある場合はHTTP例外にしません。
XAMPP等も直接ローカル接続で使用し、LAN・トンネル・未申告プロキシで公開しないでください。
開発HTTPだけSecure属性を外し、それ以外のCookie保護を維持します。

## 管理セッション

- 名前は`pollyanna_admin_`とインストールID。インストーラーの名前とは分離します。
- 保存状態にもインストールIDを結び付けます。他の設置やインストーラーのSIDを
  管理Cookieへ渡しても、既存レコードを変更せず新しい管理セッションへ切り替えます。
- IDを明示する場合は`instance_id`へ一意の32文字小文字16進数を設定します。
  同じ秘密鍵を複製して別設置を作る場合は、IDも衝突しないよう確認してください。
- CookieはHost限定、管理パス限定、HttpOnly、SameSite=Strict、本番Secureです。
- PHP設定は`session.use_cookies=1`、`session.use_only_cookies=1`、
  `session.use_trans_sid=0`、`session.auto_start=0`が必要です。不適切な場合は安全側に停止します。
  `session.use_strict_mode=1`は開始前に有効化します。
- URL・POSTに専用セッション名が指定されている場合は拒否します。
- 認証時のID再生成とCSRF更新を維持し、認証時刻・最終管理アクセスを保存します。
  無操作30分・絶対8時間で失効します。公開APIのポーリングは延長しません。
- 時計の巻き戻り、不完全な認証状態、認証情報の変更でも失効します。
- ログアウトはセッション破棄とCookie失効。パスワード変更は現在の認証をクリアし、
  他セッションも次回アクセス時の資格情報スタンプ照合で失効します。
- PHPの標準`files`保存先を使い、ネイティブハンドラーをリクエスト内でラップします。
  永続PHP設定・保存先は変更しません。全状態の読み戻し・完全一致検査は廃止しました。
  読み取り時に取得したネイティブロックを、認可・処理・最後の保存まで維持します。
- 出力と成功転送をバッファーし、終了時の保存確認が失敗した場合も503に置換します。
  設定ファイルの更新とセッション保存は一つのトランザクションではありません。
  保存障害時に設定変更が既に完了している可能性はあるため、復旧後に状態を確認します。

同一SIDの要求は直列待ちになります。長い集計等では待ち時間が生じますが、保存確認の
ためだけのロック再取得はしません。この工程ではDBセッションを導入しません。

### 保存確認と競合制御の保証範囲

旧処理は、`session_write_close()`による解放後に別要求が更新すると、読み戻した
セッション全体の比較に失敗していました。現在は開始時のreadと終了時のwrite/closeを
観測し、PHPの警告・例外とハンドラーの失敗戻り値を検出します。`session_write_close()`
単体の戻り値だけを成功判定にはしません。親`SessionHandler`へ処理を委譲するため、
標準ファイルハンドラーが取得したロックを保持したまま保存できます。

ログアウト・ID再生成では、待機要求が古いファイルを開いている場合にも古い認証を
読めないよう、ロック下で内容を空にしてからネイティブ削除を実行します。
失効した認証は再ログインなしで復活させず、CSRF検証も維持します。

保証の対象は、適切な排他ロックが機能するローカルファイルシステムの標準`files`です。
平坦な`session.save_path`と`0;MODE;path`に対応します。階層分割保存、Redis、Memcached、
独自userハンドラー等は同じ保証を自動適用せず、管理認証を503で停止します。
別方式にはロック・失敗通知・strict modeの契約を確認したアダプターが必要です。
テスト用依存注入は信頼済みPHPコードだけの機構であり、HTTPや設定の解除機能ではありません。

ネイティブハンドラーが成功を報告したことは確認しますが、電源断後の永続性、fsync、
ストレージが黙ってデータを失う障害、NFS等の排他性までは証明しません。
GCや保存期間設定によってセッションがアプリの期限より早く消える場合もあります。
実環境の権限・容量・ハンドラー・ファイルシステムは導入前の確認対象です。

別SIDのパスワード変更は、資格情報を照合する時点が認可の境界です。変更後に照合する
旧セッションは拒否しますが、変更前に認可済みの処理を途中キャンセルしません。
その処理が完了しても、次の要求では新しい資格情報で失効を確認します。
同一SIDの状態は直列化しますが、別SIDによる設定ファイルの同時更新全般を原子的にする
変更ではありません。セッション保存とDB・設定更新も一つのトランザクションではなく、
保存障害の503でも設定が既に変わっている場合があります。自動再送はしないでください。

## 設定ミスからの復旧（認証の迂回なし）

1. 管理画面へのアクセスを繰り返す前に、ファイル操作権限のある所有者が
   `config/config.php`をバックアップします。DBや認証ファイルは削除しません。
2. `admin_security.origin`を実際のHTTPS Originへ、`admin_path`をブラウザーで使う
   管理パスへ修正します。プロキシがある場合は実接続元IPと単一の上書きヘッダーを
   提供元資料で確認します。推測で全プロキシを許可しません。
3. 適切なセッションPHP設定と保存先の権限・容量を確認します。`app_secret`と
   `admin_credentials.json`は保持し、`development`へ変更して保護を解除しません。
4. PHP構文とOPcacheの反映を確認し、設定したHTTPS URLから接続します。
   通常の管理パスワードとCSRF検証を経てログインします。
5. 正しい値を確認できない場合は停止状態を維持します。復旧用の公開URL、認証省略、
   パスワード初期化、セッションファイルの一括削除は行いません。

## 配布ZIPへの後続作業

`tools/build-release.ps1`の許可リストはこの工程では変更していません。
現在の許可リストのままZIPを作ると、新しい管理画面が必要とするクラスが欠落します。
配布前に最低限`src/RequestSecurity.php`、`src/AdminSession.php`、`src/AdminSessionStore.php`、
`src/InstallerConfig.php`を追加し、
`src/RuntimePolicy.php`も後続の利用箇所と合わせて梱包対象を確認してください。
更新した設定テンプレート・移行説明が利用者へ届くことを確認し、テストコード、
実設定、認証情報、セッション、ログは含めません。
展開したZIPからの標準・サブディレクトリ設置とログインを試験するまで配布しません。

## 検証

```text
php tests/run-regression.php
php tests/admin-security-http-tests.php
php tests/admin-session-concurrency-tests.php
```

前者は通信なしの単体・回帰試験、後者は明示実行するローカルHTTP統合試験です。
HTTP試験は一意なOS一時ディレクトリにコードとダミー設定を複製し、127.0.0.1だけで
2つのサーバーを起動し、同じSIDの管理GET・設定POSTも同時に送信します。
永続DBには接続せず、実際のTLSは使わず信頼済み終端ヘッダーを
模擬します。終了時にサーバーと一時ディレクトリを片付けます。
本物のTLS・レンタルサーバー・MySQL全機能・ブラウザーのCookie送信判断を検証した
ものではありません。旧HTTPテストにはPHPSESSIDやHTTP運用を前提にしたものがあり、
今後、隔離環境向けの対応が必要です。これらを本番で実行しないでください。

並行試験は自分で作成したOS一時ディレクトリのPHPファイルセッションだけを使用し、
2〜3つのPHP CLIプロセスを起動します。7シナリオでGET相当・実設定保存関数、
ログアウト、期限境界、CSRF更新、別SIDでのパスワード変更の順序を確認し、
不要な503/RETRYは一件でも失敗にします。保存方式依存の読み取り・書き込み・closeの
失敗通知は注入したハンドラーで、破損はネイティブの一時セッションファイルでも試験します。
OSのディスク故障や電源断を再現した試験ではありません。

追加の新規設置試験は、実インストーラーの基本設定フォーム、共有の設定生成処理、
生成ファイルを使う実管理画面のログインを連結して検証します。完了・途中・未設置の
削除案内条件、日英表示、案内中のセッション不変、HTTP拒否、明示的開発例外、
大文字サブディレクトリも確認します。HTTPSは隔離した試験コードでサーバー変数を
模擬します。DB接続工程は試験用セッションで代替し、SQL実行はしていません。
MariaDBを含む完全な新規設置と実TLS・実ブラウザーは、専用検証環境での確認が必要です。
